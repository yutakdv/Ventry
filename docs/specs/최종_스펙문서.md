## 0. 서비스 정의 (확정)

### 0-1. 핵심 문장 (v4~v5 불변)
- 문제 정의: "기존 상권분석은 '어디가 좋은가'만 답한다. 창업자의 진짜 질문은 '내 형편에
  어디까지 가능한가'다."
- KB 어필: "들어갈 수 있는 곳이 아니라 **버틸 수 있는 곳**을 추천한다 — 대출을 실행하는
  은행의 관점이다."
- AI 정의: "**계산은 도구가, 판단은 에이전트가 한다.** 검증 가능해야 하는 숫자는 결정적
  계층이 만들고, AI는 무엇을 계산할지 계획하고, 결과를 해석·반박·설명한다 — 여신심사의
  의사결정 구조(승인 논리·반대 논리·조건부 판정)를 사전 상담 단계에 차용했다."
- 신뢰 계층 (★v6.2): "숫자는 결정적 계층이 만든다 → 그 결정적 설계가 실제 데이터와
  부합하는지는 오프라인 ML로 교차 검증한다(§12) → 사용자 앞에서는 AI가 설명하고 반박한다.
  서빙에 설명 불가능한 모델을 두지 않기 위한 의도된 계층 분리다."
- 표현 금지: "여신협의회를 재현" (구조 차용으로만 서술).

### 0-2. 기능 범위 (P0/P1/P2 — v6 갱신분 굵게)

| 우선순위 | 기능 |
|---|---|
| **P0 (필수)** | ① 자금 진단(폼 + 자유 텍스트 파싱 하이브리드) → ② 조달 시나리오(보수/적극) → ③ 예산 슬라이더 → ④ 입지 추천(이중 필터 + 점수화) / 마커 + 근거 패널 / 역방향 검증 / 오케스트레이터 tool-calling / 결정공간 탐색(이중 프런티어) / 리스크 검증 에이전트(1왕복 고정) / 데이터 신선도·출처 상시 표기 / **원클릭 데모 상태(데모 프로필 버튼 + 첫 세션 노출 유도) ★v6** / **README 심사 동선 가이드 ★v6** |
| **P1 (여유 시, D9~10 순서 고정)** | ① RAG 근거 인용 구현(설계는 P0 문서 확정 — §5-4) → ② 예산-후보 프런티어 미니 차트 (**발표 부재로 우선순위 근거 강화 — §0-8** ★v6) → ③ 개인화 언어화(§5-5) → ④ 쇠퇴 상권 경고 뱃지 → ⑤ 업종 추천 |
| **P2 (미룸 → 로드맵 슬라이드)** | 다회 왕복 자연어 인터뷰 / PDF 상담 리포트 / 폴리곤 히트맵 / 실매물 연동 / 전국 확장 / 상관분석 교차검증·간이 백테스트·유사 상권 임베딩 / 버스 정류장·시간대별 승하차 반영 |

> P2 항목은 문서에서 삭제하지 않고 로드맵에 명시 — "생각하지 못한 것"이 아니라 "의도적으로
> 미룬 것"으로 서술. 확장 로드맵: "창업 진입 컨설팅(현재) → 운영·이전 컨설팅(차기) — 행내
> 여신 데이터 결합 시 확장 부담률이 실제 상환 능력 기반으로 정밀화".

### 0-3. 타깃 표현 수위 (v5 불변)
- ⭕ "청년·초기 창업자에게 특히 유효한(청년 전용 자금 매칭) 서비스"
- ❌ "청년 맞춤 입지 추천". 근거 통계: 청년 창업자 약 35만 명, 감소 추세, 1순위 원인 =
  자금 문제 → "문제 시장" 프레이밍.

### 0-4. 판정 체계·용어 (전 화면·문서 공통, v5 불변)
- 판정 4단계: **적합 / 조건부 적합 / 유의 / 범위 외** ("승인" 계열 단어 전면 금지)
- 마커 3종: 🟢 적합 / 🟠 유의(부담률 초과) / ⚪ 조건부 적합(무권리 시) — 상태 추가 금지
- "심사역" → "리스크 검증", "조달 가능" → "자격 요건 부합 상품 확인(한도·승인은 기관 심사
  사항)", 자금 관련 "권장/추천" 술어 금지 → 정보 서술형
- 고정 고지: "본 정보는 공개 자료 기반 정보 제공이며 대출 권유·중개·자문이 아닙니다."

### 0-5. AI 서사 — 3단계 프레임 (★v6 귀속처 재정의)
예선에는 발표가 없다. 3단계 서사의 전달 채널을 다음과 같이 재배정한다.

```
[1] 사용자 이해      — 자유 텍스트 진단 파싱, 대화 맥락 기반 탐색 계획
[2] 결정공간 탐색    — 무엇을 계산할지 계획하고, 결정적 계산 결과를 해석·언어화
[3] 결과 검증        — 리스크 검증 에이전트의 데이터 기반 반박(1왕복),
                       정책자금 매칭의 공고 원문 근거 인용(RAG)
```

**예선 제출물 확정 (★v6.1)**: ① 기술설명서(PDF·PPT) ② 프로토타입(소스코드) ③ 참가신청서.
영상·별도 자료 제출 불가 — 서사를 실을 수 있는 채널은 아래 둘뿐이다.

| 채널 | 역할 (★v6.1) |
|---|---|
| **기술설명서** | 예선의 주 채널이자 **유일한 서사 통제 채널**. 3단계 서사 + 30초 킬러 대사(구 발표 대사) + 세부 검증을 모두 담는다 (§0-6 구조). "발표는 기억되게, 문서는 검증되게"의 역할 분리는 본선용 — 예선 문서는 두 역할을 겸한다 |
| **README + 프로토타입** | 소스코드 제출물 안에 동봉. README = 심사위원의 첫 3분 설계 (§8-1, 실행법 + 심사 동선 가이드). 프로토타입 = 무개입 탐색 전제의 AI 가시성 원칙 적용 (§0-8) |

- 순서·강조를 통제할 영상 채널이 없으므로, **정적 시각물의 비중이 상승한다**: 프런티어
  계단 차트·화면 스크린샷·3단계 다이어그램은 기술설명서 필수 요소 (§0-6).
- 본선 진출 시 발표 PPT는 기존 v5 원칙(3단계만, 세부 나열 금지)으로 복귀. 시연 영상은
  본선 무대 장애 대비 백업으로만 제작 (D13~14 → 본선 준비 기간으로 이월).

### 0-6. 기술설명서 구조 확정 (★v6 신설 · v6.1 형식 논점 추가)
발표가 없으므로 기술설명서가 질문받을 기회도, 반박당할 기회도 없다. 예상 질문에
**선제적으로 본문에서 답한다.**

0. **형식 결정 (★v6.1)**: 요강상 PDF·PPT 모두 허용. 결정 = **PPT형 기술설명서**
   (슬라이드 포맷, PDF로 내보내 제출).
   - 근거: 영상 채널이 사라진 조건에서 서사·시각물(스크린샷, 프런티어 차트, 3단계
     다이어그램)의 전달력은 슬라이드 포맷이 우위. 심사위원이 다수 팀을 연속 검토하는
     상황에서 가독 속도도 유리.
   - 밀도 보전: 수식·스키마·검증 상세는 각 장 뒤 **부록 슬라이드(Appendix)** 로 수록 —
     "기억되는 층(본문 슬라이드) + 검증되는 층(부록)"의 2층 구조. 예상_QA.md·assumptions.md
     는 리포지토리 동봉으로 검증 깊이 보완.
   - 부록 고정 2장 (★v6.2): **부록 1 「AI 평가 하네스 성적표」** + **부록 2 「LightGBM+SHAP
     설계 교차 검증」** — §12 산출물을 그대로 수록. 게이트 판정에 따른 문안 수위는 §12-3.
   - 구성비 목표: 본문 15~20장 + 부록 10~15장.

1. **장 구성**: 각 장 도입부에 「이 장은 3단계 서사 중 [n]에 해당」 표식 + 해당 화면
   스크린샷 1장. 심사위원이 문서만 읽어도 화면이 연상되고, 프로토타입만 만져도 문서
   위치를 찾을 수 있게 양방향 앵커.
2. **1장 = 매핑 표 (§1-1)**: 주제 요구사항 대조를 심사위원보다 먼저 수행 (v5 유지).

   - (룰엔진?) → "숫자를 만드는 계층은 의도적으로 결정적이다 — 그 설계가 실제 데이터와

### 0-7. 사업성·기대효과 — 1페이지 (★v6 신설)
재무 추정을 만들지 않는다. 이미 확보된 재료 두 개를 명문화한다.

- **KB부동산과의 관계 정의 (시너지 프레이밍)**:
  「KB부동산은 **매물·시세의 관점**에서 공간을 본다. 본 서비스는 **자금·지속의 관점**에서
  같은 공간을 본다. 창업자의 실제 의사결정은 두 관점이 만나는 지점 — "이 매물을, 내 자금
  으로, 버틸 수 있는가" — 에서 일어나며, 이 결합은 매물 플랫폼과 여신 역량을 함께 가진
  KB만이 완성할 수 있는 동선이다.」
  - ❌ 금지 표현: "KB부동산이 못하는", "KB부동산의 한계" 등 주최사 제품 공격 프레임.
    비교가 아니라 **결합**으로만 서술.
- **상담 관문 기대효과**: 「청년 창업자 약 35만 명, 창업 애로 1순위 = 자금. 본 서비스는
  자금 때문에 의사결정이 막히는 바로 그 지점에서 자격 부합 상품 확인 → 기관 상담으로
  연결되는 관문이다. 공개 데이터 프로토타입은 내재화 시너지(행내 여신 데이터 기반 부담률
  정밀화, 기존 여신 고객 이전·운영 컨설팅)의 하한선이다.」
- 분량 1페이지 고정. 수익 모델·시장 규모 추정은 본선 과제로 미룸 (로드맵에 1줄 언급만).

### 0-8. AI 가시성 원칙 (★v6 신설)
발표자가 접힌 카드를 열어줄 수 없다. 심사위원이 **무개입으로 훑어도** AI 개입 지점
(탐색 계획 plan / 리스크 검증 반박 / RAG 인용)이 최소 1회 시야에 들어와야 한다.

## 1. 전체 아키텍처 (스택 확정 — v5 불변)

```
[배치: Python]                  [저장]              [서빙: Spring Boot]              [프론트]
서울 상권분석 API ──┐
소진공 상가정보 CSV ─┤
```

  version 취소 — exploration spec §5). 배치 = Python(pandas/geopandas). 접점은 PostgreSQL
  덤프 하나. Docker compose에 batch 컨테이너 미포함(사전 적재 덤프 제출).
- 실시간 외부 의존 = 카카오맵 JS SDK 단 하나 (무료 쿼터, 앱키+도메인 등록, 2024-12 이후

- **구조**: doc_chunk_ref → 벡터DB 청크 조회 → 원문 그대로 표시 (LLM 재작성 금지 —
  인용은 검색이지 생성이 아니다).
- **일정 처리 (★v6 문안 이원화)**: 구현 완료 시 기술설명서에 구현 기능으로 기술.

  최대 감점 요인. 두 문안 모두 예선_QA.md에 사전 작성.

## 11. 예상 Q&A 운용 (★v6 재정의)

발표 Q&A가 없으므로 문항의 역할이 바뀐다: **심사위원이 속으로 묻고 스스로 답하기 전에,
문서가 먼저 답해야 한다.**

- **본문 선제 반영 (설계 원칙 박스 5)**: 룰엔진(§0-6-3 ①) / 대출 유도(②) / 임대료
  해상도(③) / 한도 보장(④) / 추천 신뢰(⑤) — 기술설명서 해당 장에 원칙 서술형으로 배치.
- **리포지토리 동봉 (예상_QA.md)**: 핵심 9문항 + 탐색 상세 10문항(exploration spec §9)
  전체 수록. 문서 본문 밀도를 지키면서 검증 깊이를 원하는 심사위원에게 경로 제공.
- 본선 진출 시: 예상_QA.md가 그대로 발표 Q&A 대비 자료로 승격 — 이중 활용.

핵심 9문항 요지 (전문은 예상_QA.md):
1. "이 예산이면 이 상권이 된다는 근거는?" → 4블록 출처 기반 추정 + 구간 + 이중 필터.
2. "AI가 하는 일이 정확히 뭔가?" → 3단계: ① 사용자 이해(파싱·탐색 계획) ② 결정공간
   탐색(계획·해석·언어화) ③ 결과 검증(리스크 반박·원문 인용). 숫자는 결정적 계층.
3. "기존 상권분석과 뭐가 다른가?" → 질문 순서 뒤집기 + 결정 지형 전체 계산 + 상환 부담 반영.
4. "추천이 맞는지 어떻게 아나?" → 가중치 공개·조정 가능 / 민감도 분석(±20%, θ 변동 포함
   ★v6) / 리스크 검증 통과·반영 상태로만 노출 / **오프라인 ML 교차 검증 — 매출을 입력하지
   않은 점수 축이 추정매출을 설명하는지 + SHAP 방향이 설계 부호와 일치하는지 확인, 사전
   등록 게이트 통과 수위로만 수록(부록 2) ★v6.2**. 정밀 백테스트(시계열 실적 검증)는 행내
   데이터 결합 로드맵.
5. "대출 한도를 어떻게 보장하나?" → 보장하지 않음. 자격 부합 판정만, 상담 관문.
6. "대출을 더 받으라고 유도하는 것 아닌가?" → 상향 인사이트는 지속 후보 수·하향 마진·
   고지와 항상 동반.
7. "결국 파라미터 루프 아닌가?" → 샘플링 없음. 비용 정렬 닫힌 형태 + 조달·지속 제약 최적화.
8. "임대료가 상권 단위 평균인데 정확한가?" → 의도된 해상도 설계. 변별은 구역, 임대 수준은
   상권. 출처·해상도 화면 표기, KB 내재화 시 정밀화 지점.
9. "교통·생활 인프라는 어떻게 반영했나?" → 대중교통 유입 = w1 세 번째 성분(승하차 ×
   거리 감쇠), 생활 인프라 = 집객시설. 매핑 표(§1-1) 제시.

## 12. AI 품질 검증 계층 — 평가 하네스 + ML 교차 검증 (★v6.2 신설 · 배치/문서 전용)

**서비스 기능이 아니다.** P0/P1 표(§0-2)·API 계약(§6)·Spring 서빙·UI에 변경이 없고,
배치(Python) 스크립트 `batch/eval/`과 기술설명서 부록 1·2, README 3줄(§8-1)에만 존재한다.
목적은 하나 — 본 기획의 AI 품질 주장(매칭 정확도·근거 충실도·점수 설계의 데이터 정합)을
**심사위원이 재현 가능한 숫자**로 바꾸는 것. 새 기능이 아니라 "우리 AI의 성적표"다.

- 신뢰 계층(§0-1 재기술): 결정적 계산이 숫자를 만들고 → 그 설계를 ML이 오프라인에서
  교차 검증하고 → 사용자 앞에서는 AI가 설명·반박한다. 검증용 모델은 서빙 경로에 올라가지
  않는다 — 설명 불가능한 모델을 서빙에 두지 않기 위한 계층 분리가 이 기획의 정체성이며,
  ML은 그 분리가 데이터와 부합함을 증명하는 도구로만 쓴다.

### 12-1. 평가 하네스 — `make eval` 1회 실행

| 항목 | 정의 | 골드 기준 | 비고 |
|---|---|---|---|
| 자격 매칭 P/R | eligibility_filter 판정 vs 수작업 골드 라벨의 Precision/Recall | 가상 프로필 12~20종 × 상품 전건 교차 판정표 (D9~10 작성) | 결정적 필터의 회귀 테스트 겸용 |
| 추출 정확도 | LLM 구조화 초안 필드 vs 사람 검수 확정본의 필드 일치율 | 기존 전건 검수 결과(§3-1)가 그대로 골드 — 추가 라벨링 0 | "비정형 공고 → 구조화 DB" 파이프라인의 정량 근거 |
| 근거 충실도 | 응답 source_quote ↔ 벡터DB 원문 청크의 문자열 일치율 | 원문 청크 (완전 일치 원칙) | "인용은 검색이지 생성이 아니다"(§5-4)의 계량화. RAG 미구현 시 §5-4 이원화 문안 준용("설계 확정·본선 반영") |
| 민감도 분석 | 가중치 ±20%·θ 변동 시 상위 3곳 순위 유지율 | — (기존 D10 스크립트 편입, 실행 불변) | §4-3 |
| 검증 모델 지표 | §12-2 프로토콜의 R²·ρ·WAPE·MAE·SHAP 방향 일치 | §12-3 게이트 | 게이트 C 판정 시 성적표에서 해당 행 제외 |
| (참고) 점수-매출 순위 정합 | 비매출 성분 점수 ↔ 추정매출 Spearman ρ | — | w2·w5는 매출 파생이라 포함 시 순환 참조 → 제외하고만 산출 |

- 출력: `metrics.json` + 차트 PNG → **부록 1 「성적표」 1장**으로 그대로 수록.
- Makefile 타깃: `eval-matching / eval-extraction / eval-grounding / eval-sensitivity /
  eval-model` + 통합 `eval`. 전부 기존 적재 테이블·검수 산출물을 **읽기만** 한다 —
  서비스 데이터 파이프라인·DB 스키마 무변경.

### 12-2. LightGBM + SHAP — 설계 교차 검증 (오프라인 배치)

**추천 엔진을 교체하지 않는다.** "서비스를 위한 AI"가 아니라 **"설계를 검증하는 AI"** —
추천은 기존 결정적 계산, 검증은 LightGBM(오프라인 배치), 설명은 SHAP(정적 이미지, 부록
전용). 서빙 코드·API·UI 영향 0, `lightgbm`·`shap` 의존성은 배치 requirements에만 추가.

검증 질문: **"매출을 입력하지 않은 우리 점수 축(수요·경쟁·성장)이 실제 추정매출을
설명하는가, 그리고 기여 방향이 설계 부호와 일치하는가."** 평가 프로토콜은 결과 확인 전에
사전 고정한다 (assumptions.md 등재):

1. **타깃** = log(월 점포당 추정매출). 총매출은 점포수와 준항등 관계라 검증력이 없고,
   "한 점포가 버틸 수 있는가"라는 서비스 의미론과도 점포당 매출이 정합.
2. **피처** = 점수 설계의 비매출 성분만: w1 3성분(길단위 유동·상주/직장·교통유입) + w3
   경쟁밀도 + w4 상권변화 (+선택: 임대료 — fallback 플래그 행 제외). **w2·w5는 매출
   파생이므로 데이터 누수로 배제** — 넣는 순간 자기 자신을 예측하는 순환이 된다.
3. **검증** = 자치구 블록 5-fold 그룹아웃 CV. 공간 자기상관 탓에 랜덤 CV는 성능을 과대
   평가한다 — 낮더라도 정직한 숫자를 쓴다 (심사 문답의 방어선).
4. **지표** = fold 중앙값 R² / Spearman ρ(순위 서비스와 의미 정합) / WAPE·MAE(만원 단위,
   보고용) / 베이스라인(자치구 평균 예측) 대비 개선. **MAPE 미사용** — 저매출 구역 분모로
   수치가 폭발·왜곡되는 우측 꼬리 분포.
5. **SHAP** = summary plot 1장 + 축별 기여 방향 부호 vs 설계 부호의 일치 수(5축 중 n).
   가중치 "크기"의 일치까지는 주장하지 않는다 — 방향·상대 중요도 수준의 정합만 서술.

- 한계 명기(부록 2 하단 고정 문구): "타깃인 추정매출 자체가 카드 데이터 기반 공표 추정치
  이므로, 본 검증은 '설계와 공개 데이터 세계의 정합' 확인이며 실매출 예측력 주장이 아니다.
  서비스의 모든 숫자가 동일 데이터 위에서 작동하므로 이것이 정확한 검증 범위다."

### 12-3. 수록 게이트 (사전 등록 — 결과 확인 전 고정)

| 판정 | 조건 (공간 CV fold 중앙값) | 기술설명서 서술 수위 |
|---|---|---|
| **A 본검증 수록** | R² ≥ 0.30 **그리고** ρ ≥ 0.60 **그리고** SHAP 방향 일치 ≥ 4/5축 | 부록 2 전체 + 박스 ① 보강 문장 유지 — "설계-데이터 정합을 설명력·방향 양면에서 확인" |
| **B 참고 분석** | R² ≥ 0.15 **그리고** (ρ ≥ 0.45 **또는** 방향 일치 ≥ 4/5축) | 부록 2 축소(방향 일치 중심 반 장) — "방향 정합 확인, 설명력은 참고 수준" + 한계 문구 필수 |
| **C 미수록** | 그 외 | 부록 2 삭제·성적표 행 제외, 민감도 분석 단독 유지(v6.1 상태 복귀). 박스 ①은 "서빙 무모델 원칙"만 잔류. 신호 없는 모델의 SHAP 방향 주장은 방어 불가하므로 함께 폐기 |

- 게이트 설계 근거: ① 수치는 §12-2 프로토콜(비매출 피처·점포당 로그 타깃·공간 CV)에
  조건부다 — 프로토콜이 느슨하면 같은 모델도 R² 0.2 이상 높게 나오므로, 임계치보다
  프로토콜 고정이 선행한다. ② 횡단면 사회경제 데이터 + 공간 CV에서 R² 0.3대는 강한
  신호로 통용된다(행동과학 관례상 R² ≈ 0.26이 대효과 경계). ③ 순위 기반 서비스이므로
  R² 단독이 아니라 순위상관 ρ를 공동 조건으로 둔다 — R²는 높은데 순위가 흐트러지는
  결과의 과대 서술을 차단.
- 심사 서사: "성능을 자랑하려는 모델이 아니라 **설계를 반증 시도한 모델**이다. 그래서
  기준을 결과 확인 전에 등록했고, 미달하면 싣지 않는다." — 판정 결과와 무관하게 방법론
  자체가 점수가 되는 구조.

### 12-4. 공수·후퇴 규칙

- 공수(전부 배치·문서 트랙, 서비스 일정 간섭 0): 골드셋 반나절(D9~10 틈새) / 학습+SHAP
  반나절 / 하네스 조립·Makefile 반나절 / 부록 1·2 슬라이드 D13 반나절.
- 후퇴 순서(시간 압박 시): ① 근거 충실도(RAG 연동분) → §5-4 이원화 문안으로 전환
  ② 검증 모델 → 게이트가 자동 처리(C 판정 = 미수록이 정상 동작) ③ 골드셋 12종으로 축소.
  **민감도 분석은 기존 P0 QA이므로 최후까지 유지** — 하네스 전체가 후퇴해도 기획안은
  v6.1 상태로 정확히 복귀하며, 서비스에는 어떤 흔적도 남지 않는다.
