(이후에는 CONTRIBUTING §6 계약 변경 절차). 각 항목의 "반영 위치"는 이미 수정된 파일이다.

- **§8~§11**: D2(2026-07-21) FE 계약 검토 의견 반영분 — 계약이 아직 동결 전(D3 CP1)이므로
  CONTRIBUTING §6 사후 절차가 아니라 **예정된 CP1 검토 창구**로 처리했다.

## 1. 판정 용어 = "유의" (enum `CAUTION`)

- **문제**: 스펙 v6.2·탐색 스펙은 "유의", CLAUDE.md·README·API 계약·태스크 문서는 "정속"으로
  갈라져 있었음. 용어 컴플라이언스는 심사 감점 직결 항목.
- **확정**: 판정 4단계 = `적합 / 조건부 적합 / 유의 / 범위 외`. API enum은
  `FIT / CONDITIONAL / CAUTION / OUT_OF_SCOPE` ("SLOW" 폐기).
- **근거**: "문서와 코드가 어긋나면 스펙 문서가 우선"(CLAUDE.md) + "유의"가 심사위원에게
  자명한 표준 용어.
- **반영**: CLAUDE.md · README.md · API_CONTRACT.md · TASKS.md · tasks/FRONTEND.md.
- **할 일**: FE — 화면 문구·마커 라벨에 "정속" 사용 금지. BE — Verdict enum `CAUTION`.

## 8. 진단 폼 신규 3필드 — 수치는 구조화 필수 (2026-07-21, FE 제안 ①)

- **문제**: 화면 1이 받는 입력 중 재창업 여부·담보 제공 가능 여부·월 투자 가능액 세 가지가
  `form`에 자리가 없었다. FE는 이 값들을 `free_text`에 실어 보내는 우회안을 제시했다.
- **확정**: 세 필드 모두 `form`에 구조화한다.
  - `monthly_investable`(int, 만원) — **자유 텍스트 경유 불가**. "250만원"을 LLM이 250 /
    2,500,000 / 누락 중 무엇으로 뽑을지가 비결정적이며, 이는 LLM이 수치를 만드는 통로가 되어
    불변 원칙 §0-1과 정면 충돌한다. FE의 지적이 정확하다.
  - `is_existing_business`(bool) — 자격 정규칙 축이다. 스펙 §5-4의 인용 예시가 이미
    "만 39세 이하 **예비창업자**로서…"이므로 예비창업자 한정 상품을 거를 근거가 된다.
    `Eligibility.pre_startup_only`로 EligibilityFilter에 즉시 결선.
  - `collateral_available`(bool) — 스펙에 담보 축이 없어 **현재 판정에 쓰지 않는다.** 프로필로
    기록만 하고 BE-04 조달 검증의 보조 입력으로 예약한다. 계약 문서에 "미사용"을 명시해
    "받아놓고 안 쓰는 필드"임을 숨기지 않는다.
- **미사용 필드 처리 원칙**: `monthly_investable`도 현 시점 계산에는 쓰이지 않는다. BE-04에서
  한계 조달의 월 상환액 m에 대한 상환 여력 상한(m ≤ monthly_investable)으로 결선하며,
  그때 가정으로 assumptions.md에 등재한다.
- **반영**: API_CONTRACT.md 엔드포인트 1 · tasks/BACKEND.md BE-04.

## 9. 예산 프리뷰의 주체 = `POST /budget` 응답 (2026-07-21, FE 제안 ②)

- **문제**: 화면 2의 예산 슬라이더가 즉시 프리뷰(예상 후보 수·임대료·유동인구)를 그리는데
  `POST /budget`에 응답 스키마가 없었다. FE가 "/budget이 주는가, 프론트가 /recommend를
  재호출하는가"를 아키텍처 결정 사항으로 물었다.
- **확정**: **`POST /budget` 응답이 프리뷰를 준다** (FE 선호안과 동일).
- **근거**: `/recommend`는 세션의 확정 예산 B₀로 계산한다. 화면 2 시점에는 B₀가 아직 없어
  자기자본으로 폴백하므로, 슬라이더가 가리키는 임의 예산의 프리뷰를 **원리적으로** 만들 수
  없다. `/recommend?budget=` 쿼리로 우회하면 예산의 진실 원천이 세션과 쿼리로 이중화되어
  `/explore`(세션 B₀ 기준)와 어긋난다.
- **부수 확정**: B₀는 덮어쓰기다. 화면 2 슬라이더는 debounce 후 `POST /budget`을 반복 호출하고
  마지막 값이 확정값이 된다. 화면 3 슬라이더는 스펙 §7·expl §5대로
  `POST /budget` → `/recommend?v=`·`/explore?v=`(동일 version) 순서를 유지한다.
- **반영**: API_CONTRACT.md 엔드포인트 3.

## 10. `/recommend` 정렬·필터 = 클라이언트 처리 (2026-07-21, FE 제안 ③)

- **확정**: 응답 필드는 FE 요청분(`score`·`total_count`·`summary` + area별 `monthly_rent`·
  `est_sales`·`daily_floating`)을 **전부 추가**하되, 정렬·필터 **쿼리 파라미터는 두지 않는다.**
- **근거**: ① 정렬·필터에 필요한 값이 모두 응답에 실리므로 프론트가 왕복 0회로 처리할 수 있고,
  그편이 스펙 §7의 "<100ms 재계산 체감" 목표에 유리하다. ② 서버 정렬·필터를 두면
  `total_count`·`summary`의 기준 집합이 파라미터마다 달라져 계약이 복잡해진다.
- **재검토 시점**: BE-02 실데이터 전환으로 후보 풀이 커져 페이징이 필요해지면 그때 도입한다.
- **부수 정정**: `burden_ratio`를 픽스처 상수에서 **환산임대료 ÷ 추정매출 파생**으로 바꿨다.
  스펙 §4-2의 정의 그대로이며 AI-05 산출물(부담률 분모·분자)과도 정합한다.
- **반영**: API_CONTRACT.md 엔드포인트 4 · assumptions.md #8.

## 12. 팀 표결 대체 — AI 파트 단독 확정 5건 (2026-07-25)

D6 시점에 열려 있던 AI·CM 이슈 5건(#72·#21·#65·#22·#26)을 **표결 대기 없이 AI 파트가 확정**하고
근거를 문서에 남기는 방식으로 처리했다. 각 결정은 "되돌리는 조건"을 함께 적어, 이견이 생기면
문서를 고치고 코드를 되돌리는 경로를 열어 둔다.

- **D-A. 소진공 변동금리 `rate` 를 공시 표값으로 채운다** (#72)
  - 근거: 융자공고가 지목한 「금리안내」 표(‘26년 3/4분기 기준금리 3.85%)가 이미 수집 원문
    `소진공_소상공인정책자금_지원사업안내.txt` 에 수록돼 있다. 표의 「금리」 열 값을 그대로 옮기며,
    기준금리+가산을 직접 계산하지 않는다. 2차 출처(블로그)는 §0-1 미충족으로 미채택.
  - 되돌리는 조건: 분기가 바뀌면(1·4·7·10월 10일) 값이 낡는다 → `rate_note` 의 적용 분기를 보고
    재수집·갱신한다. 갱신 전까지는 표기된 분기 기준으로 읽는 것이 정확하다.
  - 반영: assumptions #34 · `20_finance.sql` rate NULL 14→7.

- **D-B. 골드셋 수치는 제거가 아니라 의미 정렬로 고친다** (#72)
  - 근거: 서울신보 골드의 `rate` 는 **보증료율**이었다. 값이 틀린 게 아니라 필드 의미가 어긋난
    것이므로, 재수집 원문의 `[보증료]`/`[대출금리]` 라벨로 전건 대조해 재배치했다.
  - 되돌리는 조건: `rate` 의 정의(월 상환액용 연 대출금리)가 바뀌면 전면 재검토.
  - 반영: assumptions #33.

- **D-C. 서울신보는 OCR이 아니라 웹 재수집으로 해결한다** (#72)
  - 근거: tesseract 미설치이며 설치는 심사 환경 재현성을 해친다. 웹 본문은 인쇄본보다 오히려
    1차 출처에 가깝고 §5-4("인용은 검색이지 생성이 아니다")에 정합한다.
  - 되돌리는 조건: 서울신보가 페이지 구조를 바꾸면 `funding_web.py` 의 본문 앵커를 조정한다
    (텍스트를 손으로 고치지 않는다 — 원문 verbatim 원칙).
  - 반영: assumptions #32.

- **D-D. AI-08 프로토콜·게이트를 모델 코드보다 먼저 커밋한다** (#21)
  - 근거: §12-3의 방어선은 임계치가 아니라 **"결과를 보기 전에 등록했다"는 커밋 순서**다.
    순서가 뒤집히면 게이트의 심사 가치가 0이 된다(리스크 #19 — 사후 조정 금지).
  - 되돌리는 조건: 없음. 프로토콜 변경이 불가피하면 **실행 전** assumptions 재등록만 허용한다.
  - 반영: assumptions #35, 커밋 순서.

- **D-E. #65(창업비용 단위·가맹점 편의)는 3인 표결 없이 확정 종료한다**
  - 근거: 근거가 assumptions #38~#41(재채번 전 #21~#24)에 등재됐고 코드·라벨 반영은 PR #70에서
    병합 완료다. 남은 것은 형식적 동의뿐이라 이슈를 더 여는 실익이 없다.
  - 되돌리는 조건: 원 통계(KOSIS 음식점업 총액) 대조에서 단위 판정이 뒤집히면 재개.
  - 반영: assumptions #38~#41 · `load/serving.py` 의 `data_source_meta` 라벨.

## 13. 실테이블 결선 전제 2건 — 금리 미상 상품 · 시나리오 상품 선택 (2026-07-26)

표면화되는 문제라 결선과 같은 PR에서 반영한다.

### 13-1. 확정 이율이 없는 상품(7건) — 조달 조합 제외 · 자격 목록 노출

적재 26건 중 **7건이 `rate = NULL`** 이며, 전부 "은행금리에서 X% 차감" 형태라 **절대 금리를
알 수 없다**(F-002·F-004·F-005·F-006·F-008·F-010·F-011). 기준금리를 지어내지 않는다는 원칙은
이미 assumptions #34 에 있다.

- **조달 시나리오 편성에서는 제외한다.** 월 상환액 m을 계산할 수 없으면 상환 여력 상한
  (`m ≤ monthly_investable`, assumptions #23)을 검증할 수 없고, 검증하지 못한 조달을 기회로
  제시하는 것은 하향 안전 마진 원칙에 어긋난다. 구현은 `FundingProduct.hasKnownRate()` 게이트
  (`FundingCheck.coverWithReason`, 실패 사유 `RATE_UNKNOWN`).
- **자격 요건 부합 상품 목록에는 남긴다.** 자격 축은 연령·업종·지역·예비창업이지 금리가 아니다.
  금리를 모른다는 이유로 자격 자체를 부정하면 서울신보 주력 보증상품 6건이 화면에서 사라진다.
  DTO 는 `rate=null` + `rate_type="variable"` + `rate_note` 원문을 그대로 실어 화면이
  **"금리 미공시(한도·승인은 기관 심사 사항)"** 로 표기한다.
- 기각한 안: **대표금리 대입** — 수치 조작에 해당해 스펙 §0-1 위배. 논의 대상이 아니다.
- 되돌리는 조건: 기관이 절대금리를 공시하면 검수본에 반영해 `rate` 를 채운다.
- 반영: `EligibilityFilterTest.unknownRateProduct_stillQualifies_soItCanBeListed` ·
  `CoverOutcomeTest` (`RATE_UNKNOWN`) · 이슈 #82

### 13-2. 조달 시나리오 상품 선택 = 「필요분 최소 커버」

현행 규칙(assumptions #25)은 **"보수 = 보증형 중 한도 최대 / 적극 = 전체 중 한도 최대"** 다.
데모 픽스처(한도 1,500·3,000)에서는 문제가 없었으나 실테이블에는 **한도 8억 보증상품이 3건**
(F-004·F-007·F-008) 있어, 그대로 결선하면 소상공인 카페 창업에 **8억 보증을 제시**하게 되고
데모 서사(보수 6,500 / 적극 8,000, expl §8)도 성립하지 않는다.

- **개정**: 보수 = 보증형 중 **부족분을 커버하는 최소 한도** 상품 / 적극 = 전체 중 **부족분을
  커버하는 최소 한도** 상품. 부족분 = 필요 예산 − 자기자본. 커버하는 상품이 없으면 그중
  한도 최대로 폴백한다.
- 근거: 이 서비스가 답하는 질문은 **"내 한도로 어디까지 가능한가"** 이지 "얼마나 크게 빌릴 수
  있는가"가 아니다. 필요분을 넘는 조달을 기본값으로 제시하는 것은 상향 인사이트를 단독 노출하지
  않는다는 원칙(CLAUDE.md §3)과도 어긋난다.
- 기각한 안: **한도 상한 캡(부족분 × N)** — N의 근거가 없어 θ처럼 "통용 기준" 후퇴가 또 필요해진다.
- 되돌리는 조건: 사용자가 의도적으로 상향을 요청하는 동선이 생기면 그 경로에서만 한도 최대를 쓴다.
- 반영: assumptions #25 개정 · `ScenarioBuilder` · 이슈 #87

### 13-3. 시나리오 카드 — 라벨은 '수단', 초기값은 '필요분' (2026-07-26, 이슈 #90)

§13-2 를 실데이터에 적용해 기동한 결과 두 가지가 드러났다. 둘 다 규칙의 결함이 아니라
**가용 상품 구조가 그렇다는 사실**이었고, 왜곡하지 않는 쪽으로 정리했다.

**관측** (데모 프로필: 자기자본 5,000 · 카페 · 서울 마포구)

| 카드 | 예산 범위 | 편성 |
|---|---|---|
| 보수 | 5,000 ~ 15,000 | KB소상공인 보증서대출 10,000만 (연 2.1%) |
| 적극 | 5,000 ~ 10,000 | 대환대출 5,000만 (연 4.5%) |

필요분은 보수 1,713만·적극 3,398만인데(카페 진입 비용 중앙값 권리금 제외 6,713·포함 8,398),
**확정 이율이 있는 보증형의 최소 한도가 1억**이라 보수 카드가 더 큰 예산을 갖게 됐다.

**결정 ①  라벨은 금액의 대소가 아니라 수단이다.**
보수 = 보증형만, 적극 = 전체 상품. 두 카드의 후보 풀이 다르므로 **적극 ≥ 보수라는 보장이 없다**.
크기 순서를 억지로 맞추려면 (a) 적극에 하한을 걸어 보수와 동일해지거나 (b) 필요분을 넘는
상품을 일부러 고르게 되는데, 둘 다 사실을 왜곡한다. 화면은 두 카드를 **수단의 차이**로 서술한다.

**결정 ②  슬라이더 초기값 = `budget_min` + 필요분.**
구 규칙은 `budget = budget_max`(한도 전액 활용 가정)였다. 가용 상품의 최소 한도가 필요분보다
크면 **과잉 조달이 기본 선택**이 된다 — 위 사례에서 보수 카드의 기본값이 1.5억이 된다.
초기값을 필요분에 맞추면 실측 보수 6,713 · 적극 8,398 로 시장 진입 비용 중앙값에 안착한다.
상한은 그대로 노출하므로 사용자가 올릴 수 있고, 상향은 여전히 사용자의 선택이다.

- 계약 영향: `budget` 필드의 **값 의미 변경**(타입·이름 불변). `API_CONTRACT.md` 갱신 + FE 공지.
- 기각한 안: 적극 한도 ≥ 보수 한도 불변식 — 실데이터에서 두 카드가 동일해져 카드가 무의미해진다.
- 되돌리는 조건: 소액 보증상품이 적재되어 보증형 최소 한도가 필요분 수준으로 내려오면 재검토.
- 반영: `ScenarioBuilder` · `ScenarioBuilderTest` · assumptions #25 · 이슈 #90

**미해결로 남긴 것 — 대환대출 편성** (#90 문제 2)
적극 카드가 대환대출을 골랐다. 기존 대출을 갈아타는 상품이라 예비창업자 맥락에 맞지 않으나,
`finance_product` 에 "기존 대출 보유자 한정"을 나타낼 축이 없다(`pre_startup_only` 는 반대 방향).
D10 기능 동결이 임박해 **스키마 변경 없이는 결정적으로 거를 수 없다**고 판단해 이월한다.
임시로 상품명 블랙리스트를 넣는 것은 자격 판정을 코드에 숨기는 것이라 채택하지 않았다.
