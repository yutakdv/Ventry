> 리뷰 일자: 2026-07-29 (D10 기능 동결일) · 리뷰 기준: 현재 `develop` 브랜치 소스코드 + 리포지토리 문서

> 평가 원칙: 구현된 코드만 평가. 미구현 기능은 감점하지 않되, **현재 구현만으로 핵심 아이디어가
> 증명되었는가**를 최우선 기준으로 본다.

## Executive Summary

**"내 한도로 어디까지 가능한가"라는 질문 전환을 결정적 계산 계층 + 검증 가능한 AI 통제 구조로
끝까지 구현하고, 그 품질 주장을 재현 가능한 숫자(`make eval`)로 바꿔낸, 예선 기준을 상회하는
완성도의 프로토타입이다.**

---

## Overall Evaluation

이 프로젝트의 결정적 차별점은 기능 목록이 아니라 **주장과 구현의 일치율**이다. 대부분의 공모전
프로토타입은 "AI가 검증한다", "환각을 방지한다"를 문서에만 쓴다. Ventry는 그 주장을
서버 코드의 기계적 게이트로 강제하고(`RefinePrompt.sanitize`의 양방향 수치 집합 검증,
`ReviewPrompt.sanitize`의 입력 밖 수치 폐기), 그 품질을 사전 등록된 게이트가 있는 평가
하네스로 계량하며(부록 1·2), 수치가 나빠졌을 때 나빠진 값을 그대로 보고한다(coverage
1.000→0.846, 민감도 1.000→0.917). 이 정직성의 일관성은 심사위원이 어느 파일을 열어도
확인되는 수준이다.

리스크는 하나로 수렴한다: **서빙 경로의 LLM 역할이 의도적으로 좁아서**(축 선정 · 문장 언어화 ·
반박 1왕복), "AI 활용도"를 표면적으로 채점하는 심사위원에게는 룰 기반 시스템으로 보일 수 있다.
팀은 이 리스크를 스스로 리스크 레지스터 #7·#16으로 등재하고 설계 원칙 박스 ①·AI 가시성
원칙(§0-8)·README 도슨트 가이드로 대응해 두었다. 대응 설계는 충분하나, 전달이 문서·화면
연출에 전적으로 의존하므로(예선 무발표) 남은 5일의 화면 캡처·PPT 변환 품질이 실질 변수다.

## Strengths

### S1. "숫자는 결정적 계산이 만든다"가 문서가 아니라 코드로 강제된다

- **Finding**: LLM 출력의 수치 무결성이 프롬프트 부탁이 아니라 서버 측 기계 검증으로 강제된다.
- **Evidence**: `backend/src/main/java/com/ventry/api/llm/RefinePrompt.java:87-118` — 언어화
  교체본은 템플릿과 **수치 집합이 양방향으로 동일**해야 통과(새 수치 금지 ⊆ + 필수 수치 누락
  금지 ⊇, 지속 후보 수 누락 시 상향 인사이트 단독 노출이 되므로).
  `ReviewPrompt.java:81-108` — 반박문의 숫자 토큰이 입력 사실에 전부 존재하지 않으면 응답
  전체 폐기. 금지어("승인"·"권장"·"보장"·"추천")는 `LlmResponses.BANNED_TERMS` 단일 상수로
  두 검증기가 공유. LLM 부재 시 `NoLlmClient` → 템플릿이 최종본.
- **Impact**: "환각 어떻게 막나"라는 필수 질문에 구조적 답을 가진 팀은 드물다. 예선 통과의
  핵심 논거이자 본선 기술 문답의 방어선.
- **Recommendation**: 기술설명서 7장에 이미 반영됨. `sanitize` 코드 스니펫 1개를 부록에
  직접 인용하면 "코드만 봐도 전달되는" 증거가 완성된다.

### S2. AI 품질 주장이 재현 가능한 숫자로 존재하고, 나빠진 수치를 그대로 보고한다

- **Finding**: `make eval` 하네스가 추출 정확도·근거 충실도·민감도·설계 교차 검증을 실측하고,
  게이트(§12-3)를 결과 확인 전에 등재했으며, 수치 하락(coverage 1.000→0.846, 민감도
  1.000→0.917)을 은폐 없이 보고한다.
- **Evidence**: `ai/eval/` 스위트 5종 + `ai/eval/out/{metrics.json, *.png}` 실존,
  `docs/부록1_2_평가성적표.md`(재산출 이력 3차까지 기록, 클린 클론 재현성 실측 포함),
  `docs/기술설명서_원고.md` 8장.
- **Impact**: "추천을 어떻게 믿나"에 대해 주장이 아니라 성적표로 답한다. 사전 등록 게이트는
  심사위원(특히 데이터 배경)에게 방법론 자체가 점수가 되는 구조.
- **Recommendation**: 부록 1의 표를 기술설명서 본문 8장에 그대로 실었으니, PPT 변환 시 수치
  표가 이미지로 깨지지 않게만 주의.

### S3. 심사위원 실행 시나리오에 대한 다층 폴백

- **Finding**: 외부 의존이 전부 없어도 동선이 죽지 않는다 — OpenAI 키 없음 → 템플릿 최종본 +
  "검증 생략" 표시, 카카오 키 없음 → 지도 포기하고 목록 동선 유지, API 다운 → FE 목 폴백 +
  전역 배너.
- **Evidence**: `frontend/src/lib/useKakaoLoader.ts:9`("지도 없이도 화면이 죽지 않아야 한다"),
  `frontend/src/api/client.ts:44,65,83,133`(엔드포인트별 목 폴백 + `markApiFallback`),
  `frontend/src/components/layout/AppShell.tsx:17`(폴백 상태 상시 노출), README "API 키
  없이도 전 동선이 동작합니다" 명시.
- **Impact**: 예선은 심사위원이 직접 실행한다(무발표). 실행 실패 = 채점 실패인 조건에서 이
  다층 폴백은 사실상 보험이다.
- **Recommendation**: 폴백이 조용히 목 데이터를 보여주는 경로는 배너가 반드시 보이는지 최종
  캡처에서 확인할 것(목 수치를 실데이터로 오인하게 하면 역효과).

### S4. 테스트·QA가 실데이터 계약을 게이트한다

- **Finding**: 단위 테스트를 넘어, 실적재 덤프를 직접 파싱하는 골드 테스트와 기동 스택에 실제
  HTTP를 던지는 계약 게이트가 CI에 물려 있다.
- **Evidence**: BE 테스트 클래스 30개·메서드 238개(`EligibilityMatchingGoldTest` — 덤프
  26건 × 프로필 14종 = 364쌍), AI pytest 119개, `scripts/qa_integration.py`
  `--contract-gate`(D1+G1~G10)가 `develop-ci` compose 스모크에서 매 push 실행. 최근 CI 전부
  녹색(gh run list 확인, 2026-07-29).
- **Impact**: "프로토타입 안정성" 항목에서 감점 여지가 거의 없다. 커밋 312개·PR/이슈 188번의
  이력이 개발 프로세스 성숙도를 증빙.
- **Recommendation**: 유지. 제출 직전 클린 머신 리허설만 남았다(아래 R4).

### S5. 컴플라이언스가 화면·서버·문서 3계층에서 일관된다

- **Finding**: 판정 4단계 용어, 고지 문구, 금지어가 FE 표시 계층·BE 검증 계층·문서에서 동일하게
  강제된다.
- **Evidence**: `frontend/src/lib/verdict.ts`(적합/조건부 적합/유의/범위 외),
  고지 문구가 Scenario·Recommend·Explore·Budget·ExploreSummary 전 화면 존재(grep 확인),
  FE 소스 내 금지어 0건(주석의 규칙 설명 제외), 서버 `BANNED_TERMS`가 LLM 출력까지 차단.
- **Impact**: 금융권 심사에서 용어 실수는 즉시 신뢰 하락으로 이어진다. KB 심사위원 관점에서
  "금소법을 이해하는 팀"이라는 신호.
- **Recommendation**: 유지. 기술설명서 변환 과정에서 새 문구가 유입되지 않게 최종 스윕 1회.

### S6. 저장소 위생·시크릿 관리가 제출 수준이다

- **Finding**: 시크릿 유출 없음, 실행 진입 장벽을 낮추는 상세한 `.env.example`.
- **Evidence**: `.env`는 gitignore 확인, 추적 파일에 API 키 패턴 0건(git grep), `.env.example`이
  키 8종의 발급 URL·절차·폴백까지 안내. compose는 `${VAR:-}` 기본값으로 키 없이도 기동.
- **Impact**: 소스코드 제출물에서 시크릿 노출은 치명 감점 요인인데 해당 없음.
- **Recommendation**: 없음(현행 유지).

## Weaknesses

### W1. 서빙 AI의 체감 존재감이 얇다 — 표면 채점 시 최대 리스크

- **Finding**: 서빙 경로에서 LLM이 하는 일은 탐색 축 선정, 문장 언어화(refine), 반박 1왕복뿐이며,
  자유 텍스트 파싱은 키워드 매칭이다(`parse_source: form_only`). "AI 활용의 깊이"를 표면적으로
  보는 심사위원에게는 룰 기반 시스템 + 부가 LLM으로 읽힐 수 있다.
- **Evidence**: `docs/API_CONTRACT.md` §1(form_only 명문), `docs/기술설명서_원고.md` 2장(키워드
  매칭 자인), 서빙 LLM 코드 총량이 llm 패키지 689줄. 팀 스스로 리스크 #7("룰엔진 아니냐")·
  #16(핵심 기능 미발견)으로 등재.
- **Impact**: 예선 채점표에 "AI 기술 활용도" 같은 항목이 있다면 이 항목에서만 상대 열위 가능.
  나머지 항목의 우위로 상쇄 가능한 수준이나, 유일하게 통제가 덜 되는 변수다.
- **Recommendation**: 기술설명서에서 "AI를 얇게 쓴 것"이 아니라 **"AI를 검증 가능하게 쓰는
  공학"**이 주제임을 1장 구조에서부터 명시할 것(현 원고의 결론부 프레임을 도입부로 당기는 것 검토).
  LLM 배치 추출(29건 → 검수 → 26건, P 0.966)이 서빙 밖에서 AI가 실질 노동을 한 지점이므로
  "AI가 한 일" 목록에 배치 추출을 병렬 배치해 총량 인상을 보정할 것.

### W2. 설계 교차 검증의 방향 일치가 0/3축 — 정직하지만 오독 위험

- **Finding**: 부록 2의 LightGBM+SHAP 검증에서 게이트 B는 통과했으나 순위상관(ρ 0.556) 경로이며,
  SHAP 방향 일치는 0/3축(경쟁밀도 부호 반전 = 내생성, w4는 프록시 부호 오등재 자인).
- **Evidence**: `docs/부록1_2_평가성적표.md` 부록 2("방향 일치 0/3축", w4 정정 고지),
  `ai/eval/suites/model.py` 게이트 상수.
- **Impact**: 꼼꼼한 심사위원이 "설계가 데이터와 안 맞는다는 뜻 아닌가"로 읽을 수 있다. 팀의
  해석(내생성 → 그래서 서빙에 모델을 안 둔다)은 원고 2장 박스 ①에 이미 배치되어 있어 방어는
  성립하나, 부록만 발췌해 읽는 경우 오독 여지가 남는다.
- **Recommendation**: 부록 2 첫 문단에 "이 검증의 결론 = 데이터에 최적인 부호를 그대로 쓰면
  안 되는 이유의 실증"이라는 한 줄 요약을 최상단에 배치(현재는 결과 표 뒤에 위치). 표보다
  해석이 먼저 읽히게 순서만 조정.

### W3. 기술설명서 최종 산출물(PPT→PDF)이 아직 없다

- **Finding**: 원고(마크다운)는 10개 장 완성이나, 제출 형식인 PPT형 슬라이드 + 화면 캡처 4종
  + 프론티어 정적 차트 삽입 + PDF 내보내기가 미완이다.
- **Evidence**: `docs/기술설명서_원고.md` 작성 상태 표("남은 것은 화면 캡처 삽입뿐"),
  `docs/images/demo-{0..3}.png`는 존재하나 7장 검증 패널 캡처 등 앵커 주석 상태.
- **Impact**: 예선의 주 채널이자 유일한 서사 통제 채널(스펙 §0-5)이므로, 변환 품질이 곧
  최종 점수다. 원고 품질이 높아도 슬라이드 밀도 조절에 실패하면 전달력이 급락한다.
- **Recommendation**: D13~14 계획대로 진행하되, 본문 15~20장 제한(§0-6-0)을 지키기 위해
  원고의 서사 문단을 과감히 부록으로 내릴 것. 각 장 1스크린샷 + 1주장 + 1근거 수치 구조 권장.

### W4. 미해결 항목 3건이 문서에 남아 있다 (자인된 한계)
