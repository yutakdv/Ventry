## 2. QA 중 발견해 고친 것

### 2-1. 타입이 틀린 요청 본문이 500을 냈다 → 400

`{"form": {"age": "서른둘"}}` 이 `HttpMessageNotReadableException` → 기본 `Exception` 핸들러 →
**500 `INTERNAL_ERROR`** 로 떨어졌다. 서버 결함이 아니라 클라이언트 입력 문제이므로 400 이어야
한다. 500 이면 프론트는 재시도할지 입력을 고칠지 판단할 수 없고, 심사위원이 API 를 찔러 보는
경로에서도 없는 장애로 보인다.

`GlobalExceptionHandler` 에 전용 핸들러를 추가했다. 응답 메시지에 Jackson 예외 원문(내부
타입명·클래스 경로)을 싣지 않는 것도 함께 잠갔다(회귀 테스트 2건).

### 2-2. `parse_source` 가 LLM 을 쓰지 않고도 `"llm"` 을 보고했다

```java
String parseSource = freeText.isBlank() ? "form_only" : "llm";   // 구 구현
```

자유 텍스트가 비어 있지 않기만 하면 `"llm"` 이었다. 실제 처리는 `freeText.contains("권리금")`
키워드 매칭이고, **API 키를 완전히 지운 스택에서도 `"llm"` 이 나갔다.** 하지 않은 일을 했다고
말하는 필드였으므로 **항상 `"form_only"`** 로 고쳤다. LLM 실파싱을 붙이는 시점에 그 호출의
성공 여부로 값을 정한다.

### 2-3. `/api/recommend` 응답이 769 KB

실데이터 전환으로 후보가 목 4곳 → **1,061곳**이 되면서 응답이 769 KB 가 됐다. 슬라이더를
움직일 때마다 재호출되는 경로라 전송량이 곧 체감 반응성이다(스펙 §7 `<100ms`).

**gzip 압축을 켰다 — 769 KB → 125 KB (6.1배).** 계약도 프론트도 건드리지 않는다.
페이징은 계약 변경이라 D10 동결 전에는 하지 않는다(계약 §4 주석의 재검토 조건이다).

`text/event-stream` 은 일부러 압축 대상에서 **제외**했다. SSE 는 「템플릿 문장 즉시 송출 → LLM
refine 이 선택적으로 교체」가 설계의 핵심인데(expl §2-5) 압축이 붙으면 이벤트가 버퍼에 모였다가
한꺼번에 나갈 수 있고, 이벤트 하나가 수 KB 라 얻을 것도 없다.

## 3. 미해결 — 명시적으로 남긴다

### 3-1. LLM 3역할 중 2개가 미결선인데 API 는 수행했다고 보고한다 → **이슈 #96 (P0)**

키를 완전히 지운 스택에서 전 동선을 돌린 결과다.

| LLM 역할 (CLAUDE.md 원칙 1) | 결선 | 근거 |
|---|---|---|
| (a) 탐색 축 우선순위 계획 | ✅ | `ExploreService:71` → `llm.complete(PlanPrompt.build(...))` |
| (b) 구조화 결과의 언어화(refine) | ❌ | 계약상 **선택적 이벤트**라 미송출이 규격 준수 — 계약 위반 아님 |
| (c) 리스크 검증 반박문 생성 | ❌ | `ReasonTemplate` 이 **하드코딩 문장**을 `applied=true`·`skipped=false` 로 반환 |

문제는 미결선 자체가 아니라 **(c)를 수행했다고 보고한다는 점**이다. 계약 §4 는 `skipped` 를
"장애 시 true(검증 생략 플래그)"로 규정했는데, 검증 에이전트가 애초에 돌지 않으므로 어떤
상황에서도 `false` 다. 심사 예상 Q&A 2번이 "AI가 하는 일이 정확히 뭔가"이고 기술설명서 2장이
3역할을 명시하므로, **문서·코드 괴리**(리스크 #17)에 정확히 해당한다.

선택지와 비용은 #96 에 적었다. 요약하면 — **A** 실제 결선(인프라는 이미 있다: `LlmClient`·
`GuardedLlmClient`·`PlanPrompt` 패턴, 추가는 `ReviewPrompt` + 실패 시 템플릿 폴백 + `skipped=true`),
**B** 플래그만 정직하게 만들고 문서에서 (c)를 「설계 확정·본선 반영」으로 하향, **C** 방치(비권장).
**D10 동결 전 결정이 필요하다.**

QA 하네스는 이 항목을 **실패가 아닌 `GAP`** 으로 표시하고 매 실행에 이슈 번호와 함께 인쇄한다.
단언을 지우면 QA 는 통과하고 문제만 남으므로, 「통과」와 「미결선」을 구분해 드러낸다.

### 3-2. 대환대출이 적극 카드에 편성될 수 있다 (#90 문제 2)

기존 대출을 갈아타는 상품이라 예비창업자 맥락에 맞지 않으나 `finance_product` 에 그 축이 없다.
D10 동결 전 스키마 변경은 하지 않기로 했다 (DECISIONS §13-3).

### 3-3. `source_collected` 가 실제 수집일이 아니라 덤프 생성일 (#93)

스키마 변경 없이 값 산출만 바꾸는 일이라 동결 후 처리 가능하다.

### 3-4. 추천 후보 1,061곳을 화면이 어떻게 다루는가 — FE 판단 필요

서버는 필터 통과 후보 전량을 돌려준다(계약 §4: 정렬·필터는 프론트 소관). 지도에 마커
1,000개를 그리는 것이 타당한지는 화면 설계 문제다. 압축으로 전송량은 해결됐으나
**렌더링 부하는 별개**다. FE-04/FE-05 범위에서 확인이 필요하다.

오프라인 배치·평가 전용이다.

## 5. CI 안정성 — 이번 세션에서 3회 외부 요인 실패

코드 결함이 아니지만 **제출 시점에 발생하면 `main` 반영이 막힌다**. `develop` push 실패 시
`promote-to-main` 과 `close referenced issues` 가 통째로 스킵되기 때문이다(실제로 PR #92
병합분에서 발생해 이슈 #77·#25 를 수동 종료했다).

| 실패 | 원인 |
|---|---|
| backend-ci Docker build | Docker Hub 레지스트리 `i/o timeout` |
| develop-ci compose-smoke | Maven Central **429 Too Many Requests** |
| (재실행으로 전부 통과) | |

**권고**: 제출 직전에는 `main` 이 `develop` 과 같은 커밋인지 직접 확인한다
(`git rev-list --count origin/main..origin/develop` 이 0). 자동화를 믿고 넘기지 않는다.
