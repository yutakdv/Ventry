## 1. [BE] 무LLM 경로 재검증 (QA F2)

### 계획

**왜 지금 하는가** — 리스크 검증의 폴백 경로는 코드리뷰 조치로 **통째로 바뀌었다**:

| 이슈 | 바뀐 것 |
|---|---|
| #123 | 폴백(`skipped=true`)을 캐시에서 제외 — 이전에는 일시적 타임아웃 한 번이 「검증 생략」을 1시간 고정했다 |
| #126 | 템플릿 반박문이 판정 분포를 따라 분기 (진입 0곳 / 유의 존재 / 유의 없음) |
| #127 | 변동금리 근거는 금액 대신 `marginal_payment_note` |
| #128 | 인사이트 0건 사유를 두 갈래로 |

그런데 **그 뒤로 무LLM 스택을 한 번도 띄우지 않았다.** 지금까지의 QA 19 시나리오는 전부 키가
있는 스택에서 돌았다(`risk_review.applied=true` 로 확인). README 는 「API 키 없이도 전 동선이
동작합니다」를 **정면으로 주장**하고 있고, 스펙 §5-3·expl §2-5 의 「템플릿이 최종본」도 같은
주장이다. 검증되지 않은 주장을 제출물에 두지 않는다.

**어떻게** — 키를 비운 스택으로 api 를 재기동하고 전 시나리오를 돌린다. DB·web 은 건드리지
않는다(데이터가 같아야 두 실행을 비교할 수 있다).

**무엇을 확인하면 통과인가**

1. QA 19 시나리오 전건 통과 — 키 유무로 **규격이 갈리지 않아야** 한다
2. `risk_review.skipped=true` · `applied=false` — 사실이 그렇게 보고돼야 한다 (#96 의 본론)
3. 반박문이 **판정 분포에 맞는 템플릿** — #126 분기가 무LLM 경로에서 실제로 동작
4. **수치·판정 동일** — 키 있는 실행과 후보 수·판정 분포·진입 후보 수가 같아야 한다.
   다르면 LLM 이 필수 경로에 있다는 뜻이고, 그것은 불변 원칙 위반이다

### 개발

코드 변경 없음. 검증 전용 항목이다.

### 검토 — ✅ 통과 (2026-07-27)

```
OPENAI_API_KEY= docker compose up -d --force-recreate api
python3 scripts/qa_integration.py      → 전 시나리오 통과 (19건)
```

| 확인 | 키 있음 | 키 없음 | 판정 |
|---|---|---|---|
| QA 시나리오 | 19건 통과 | **19건 통과** | 규격 동일 |
| `risk_review` | `applied=true · skipped=false` | **`applied=false · skipped=true`** | 사실대로 보고 |
| 후보 수 | 1,059곳 | **1,059곳** | 동일 |
| 진입 후보 (6/9/15천) | [0, 707, 1055] | **[0, 707, 1055]** | 동일 |
| 판정 분포 (6,000) | 범위 외 989 · 조건부 70 | **범위 외 989 · 조건부 70** | 동일 |
| 지속 후보 수 | T1 354 · T2 122 | **T1 354 · T2 122** | 동일 |
| 자격 부합 · 인용 | 11건 · 7건 | **11건 · 7건** | 동일 |

**#126 분기가 무LLM 경로에서 실제로 갈린다** — 예산에 따라 다른 템플릿이 나온다:

| 예산 | 실제 분포 | 반박문 |
|---|---|---|
| 6,000 | 범위 외 989 · 조건부 70 | 「진입하는 후보가 없어 제시된 **70곳**은 전부 조건부 적합입니다. 무권리 매물 확보를 전제로 한 판정이므로…」 |
| 9,000 | 적합 246 · 조건부 332 · **유의 461** · 범위 외 20 | 「…추정매출 하위 시나리오에서는 부담률이 임계를 넘을 수 있습니다. **유의 판정 461곳**이 그 구간에 있습니다.」 |

구 구현이 모든 구간에서 내보내던 「유의 판정 유지가 타당합니다」 고정 문장은 사라졌고, 유의가
0곳인 구간에서는 그 단어 자체가 나오지 않는다.

**결론**: 수치·판정은 키 유무와 무관하고 달라지는 것은 **문장과 `skipped` 플래그뿐**이다.
README 의 「API 키 없이도 전 동선이 동작합니다」가 실측으로 성립한다 — LLM 은 필수 경로에 없다.

## 2. [BE] 인사이트 후보 수 자릿수 구분자

### 계획

**증상** — 서버가 보내는 T1 인사이트 문장 (2026-07-27 실측):

```
2,770만 원을 추가 확보하면 진입 가능 후보는 342곳에서 1018곳으로 늘어납니다.
```

금액(`2,770`)에는 구분자가 있는데 **후보 수(`1018`)에는 없다.** README 도슨트 대본은 같은 문장을
`1,018곳` 으로 적어 두었으므로, 심사위원이 대본을 들고 화면을 보면 **글자가 어긋난다.**
`won()` 만 `%,d` 를 쓰고 곳수는 `%d` 로 나가던 것이 원인이다.

**범위** — 화면에 나가는 문자열의 표기만 고친다. `delta` 의 숫자 필드(`n_entry_after` 등)는
**JSON 숫자이므로 건드리지 않는다** — 계약 타입이고, 화면이 자체 포맷할 값이다.

### 개발

`ReasonTemplate.count(int)` 를 두고 문장 안의 곳수 표기를 한 곳에서 만든다. 적용 지점은
`InsightBuilder` 6곳(T1 진입 전·후·지속 2, T2 2, T5 1)과 `ReasonTemplate` 3곳(반박문 분기)이다.
`won()` 과 같은 `%,d` 를 쓰되 **금액과 곳수를 이름으로 구분**해, 나중에 한쪽 규칙만 바뀌어도
다른 쪽이 딸려가지 않게 한다.

### 검토 — ✅ 통과 (2026-07-27)

실기동 문장 (예산 8,000 · 데모 프로필):

```
2,770만 원을 추가 확보하면 진입 가능 후보는 342곳에서 1,018곳으로 늘어납니다.
delta: {"n_entry_before": 342, "n_entry_after": 1018, "n_sustain_after": 354}
```

- **문장은 `1,018곳`** — README 도슨트 대본과 글자까지 일치한다
- **`delta` 는 숫자 `1018` 그대로** — 계약 타입을 지켰다. 문장만 바뀌고 값은 안 바뀐다
- 단위 테스트 추가: 1,000 이상은 구분자가 붙고 999 이하는 붙지 않는다
  (`0,070곳` 같은 표기가 나오지 않는지까지 확인)
- backend **192건 통과**(신규 1건 포함) · QA **19 시나리오 통과**
