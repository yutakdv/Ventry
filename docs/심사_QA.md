발표가 없으므로(수상 제출물 3종 확정) 이 문서는 리포지토리 동봉용이다.
핵심 5문항은 기술설명서 본문 「설계 원칙」 박스로 선제 반영(스펙 §0-6-3), 나머지는 여기서 상세화.
본선 진출 시 이 문서가 그대로 발표 Q&A 대비 자료로 승격된다 (스펙 §11).

## A. 핵심 9문항 (스펙 §11 — D13~14에 답변 최종화)

1. **"이 예산이면 이 상권이 된다는 근거는?"** — 4블록 출처 기반 추정 + 구간 표기 + 이중 필터. *(상세 답변 작성: CM-05)*
2. **"AI가 하는 일이 정확히 뭔가?"** — 3단계: ①사용자 이해 ②결정공간 탐색 ③결과 검증. 숫자는 결정적 계층.
3. **"기존 상권분석과 뭐가 다른가?"** — 질문 자체 뒤집기 + 결정 지표 전체 계산 + 상환 부담 반영.
4. **"추천이 맞는지 어떻게 아나?"** — 가중치 공개·조정 가능 / 민감도 분석(±20%·θ 변동) / 검증 에이전트 / 오프라인 ML 교차 검증(게이트 통과 시만 부록 2 수록).
5. **"대출 한도를 어떻게 보장하나?"** — 보장하지 않음. 자격 부합 확인만, 상담 관문.
6. **"대출을 더 받으라고 유도하는 것 아닌가?"** — 상향 인사이트는 지속 후보 수·하향 마진·고지와 항상 동반.
7. **"결국 파라미터 룰 아닌가?"** — 탐색 계획은 대화 맥락 기반 LLM 판단 / 비용 정렬 닫힌 형태 + 조달·지속 제약 최적화.
8. **"임대료가 상권 단위 평균인데 정확한가?"** — 의도된 해상도 설계(역할 분담 서사) + 출처·해상도 화면 표기.
9. **"교통·생활 인프라는 어떻게 반영하나?"** — 대중교통 접근성 = w1 3성분(승하차×거리 감쇠), 생활 인프라 = 집객시설. 매핑 표 제시.

## B. 탐색 상세 10문항 (exploration spec §9 전사 — 답변 완성본은 해당 문서 참조)

10. N(B) 단조 가정은 언제 깨지나 → 지속 프론티어는 비단조 (서비스 철학의 수학적 구현)
11. 경계 수치의 그리드 오차 → 그리드 없음, 정렬값 자체가 경계 (오차 0)
12. 룰엔진 아닌가 → LLM 3역할 분리는 금융 AI의 설계
13. 대출 한도 유도 아닌가 → 단독 노출 불가 구조
14. 초기비용 추정 신뢰 → 공공 출처 4블록 + 구간 + 이중 표기
15. 조달 매칭이 한도를 보장하나 → 비보장 명시, 고지 동반
16. LLM 환각은 → 수치 접근 불가 구조 + 템플릿 폴백
17. 동시 사용자 확장성 → 세션당 DB 1회 + 인메모리 100ms, 병목은 LLM(필수 경로에서 제거)
18. 분기 데이터 한계 → 구조적 의사결정에 충분 + 기준일 표기
19. KB 내재화 시 → 행내 여신 데이터 결합 로드맵 (경쟁이 아니라 결합)

## C. 아키텍처 선택 1문항 (★2026-07-25 신설)

20. **"근거 인용에 RAG(벡터 검색)를 왜 쓰지 않았나?"**
    → **검색할 질의가 없기 때문이다.** 인용 대상은 자격 필터가 이미 결정적으로 확정한 상품이고,
    상품→공고 원문 청크는 `doc_chunk_ref` 외래키로 직접 연결된다(한 문단이 여러 자금을 함께
    규정하는 공고가 있어 관계는 N:1이다). 입력이 자연어 질의가 아니라 상품 id이므로 유사도
    검색이 개입할 지점이 없다.
    더 중요한 것은 정확도다. 임베딩 유사도로 문단을 뽑으면 **다른 상품의 공고 문단이 특정 상품의
    자격 요건으로 붙는 오류**가 가능해진다. 금융상품 자격 요건 인용에서 이건 단순 오차가 아니라
    귀속 오류이며, id 직접 조회는 그 오류를 **구조적으로 만들 수 없다**. 스펙 §5-4의 「인용은
    검색이지 생성이 아니다」를 끝까지 밀면 도달하는 결론이 이것이다.
    부수적으로 pgvector 컨테이너·임베딩 배치·검색 P@k 골드셋이 전부 불필요해져, 심사위원이
    직접 실행하는 `docker compose up` 경로에 실패 지점을 추가하지 않는다.
    **재검토 시점**: 코퍼스가 수백 건 공고로 늘고 사용자가 문서에 자유 질의를 던지는 단계
    (본선·확장 로드맵). 그때는 검색이 실제로 풀어야 할 문제가 생긴다.

## 원문 근거 인용 — 구현/이월 이원화 문안 (스펙 §5-4 · CP4(D10) 판정 **전** 사전 작성)

CP4에서 BE-06 ① 원문 근거 인용의 구현 여부가 갈린다. 어느 쪽으로 판정되든 **아래 문안을 그대로**
기술설명서·README에 반영한다. **판정 후에 문안을 새로 쓰지 않는다** — 결과를 보고 서술 수위를
고르는 것을 막는 것이 사전 작성의 목적이다(§12-3 게이트와 같은 원리).

> **명칭 정정 (2026-07-25)** — 구 표기는 "RAG 근거 인용"이었으나 이 기능에는 **유사도 검색이
> 없다**. `doc_chunk_ref` 외래키로 청크를 **id 직접 조회**하는 구조이며, 벡터DB 미도입은
> [DECISIONS.md](DECISIONS.md) §7에서 3인 합의로 확정된 사항이다. 없는 기술을 쓴다고 말하지
> 않기 위해 전 문서 표기를 「원문 근거 인용」으로 통일한다 (리스크 #17).

### 문안 A — 구현 판정 시

> 근거 패널의 인용문은 자격 필터가 확정한 상품의 `doc_chunk_ref`로 공고 원문 청크를
> **그대로 조회해** 노출합니다. LLM은 인용문을 재작성하지 않으며, 화면에 표시되는 문장은
> `finance_doc_chunk.text`와 문자 단위로 일치합니다. 인용 가능한 원문이 없는 상품은 인용 없이
> 출처 기관·문서명·기준일만 노출합니다 — **없는 근거를 만들어내지 않는 것**이 이 설계의 요점입니다.

### 문안 B — 이월 판정 시

> 근거 인용은 **설계 확정·본선 반영** 항목입니다. 원문 청크 스키마(`finance_doc_chunk`)와
> 상품↔청크 연결(`doc_chunk_ref`)은 이미 적재·검수를 마쳤습니다 — **정책자금 26건 전건이 원문
> 청크 14개에 연결**되어 있고(`db/init/20_finance.sql`), 인용문은 공고문 원문 그대로입니다.
> 현재 버전의 서빙 경로는 **데모 상품 픽스처로 동작**하며, 화면에 표기되는 출처 기관·문서명·
> 기준일은 그 픽스처의 것입니다. 실테이블 결선과 인용 노출이 남은 범위이며, 이 범위에서
> 표시되는 모든 값은 공개 자료에서 결정적으로 계산된 수치입니다.

> **문안 B 사실 정정 (2026-07-25)** — 구 문안은 "남은 것은 청크를 읽어 오는 연결뿐"이라고
> 서술했으나, 실측 결과 서빙 경로는 `finance_product` 테이블 자체를 조회하지 않는다
> (백엔드 DB 쿼리는 `v_candidate_area`·`data_source_meta` 2건뿐, 자금 상품은
> `DemoProducts` 하드코딩 2건). 청크 연결 **앞에 상품 테이블 결선**이 남아 있어 문안을
> 사실에 맞게 교체했다. 사전 작성 원칙이 금지하는 것은 **결과를 보고 서술 수위를 고르는 것**
> 이지 사실 오류의 방치가 아니다 — 오히려 리스크 #17(문서·코드 괴리)의 직접 대상이다.

### 두 문안 공통

- **고지 문구 동반**: 본 정보는 공개 자료 기반 정보 제공이며 대출 권유·중개·자문이 아닙니다.
- **금지 표현**: "승인" 계열, "조달 가능"(→ "자격 요건 부합 상품 확인(한도·승인은 기관 심사 사항)"),
  자금 관련 "권장/추천드립니다"(→ 정보 서술형).
- **수치 근거**: 근거 충실도는 `make eval-grounding` 이 재산출한다. 2026-07-25 기준
  **coverage 13/29 (44.8%) · verbatim 일치율 1.0** — 인용이 붙은 건은 전부 원문과 바이트 일치이며,
  붙지 않은 건은 원문 텍스트 품질이 인용 기준에 못 미쳐 **비운 것**이다(지어내지 않았다).
