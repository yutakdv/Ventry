# 심사 예상 Q&A (20문항)

이 문서는 리포지토리 동봉용 예상 Q&A이다.
핵심 5문항은 기술설명서 본문 「설계 원칙」 박스로 선제 반영(스펙 §0-6-3), 나머지는 여기서 상세화.

## A. 핵심 9문항 (스펙 §11)

1. **"이 예산이면 이 상권이 된다는 근거는?"** — 초기비용 4블록(보증금·권리금·인테리어·예비 운영자금)이
   전부 공개 통계 출처이며, 값은 항상 구간 + 「추정」 라벨 + 출처·기준일과 함께 표기합니다.
   예산은 단독 판정 기준이 아니라 진입·지속 이중 필터의 입력입니다(산식과 출처는 기술설명서 부록 A4).
2. **"AI가 하는 일이 정확히 뭔가?"** — 배치에서 비정형 공고문을 구조화해 자금 매칭의 데이터 기반을 만들고(대체 경로 없음), 서빙 3단계: ①사용자 이해 ②결정공간 탐색 ③결과 검증. 숫자는 결정적 계층.
3. **"기존 상권분석과 뭐가 다른가?"** — 질문 자체 뒤집기 + 결정 지표 전체 계산 + 상환 부담 반영.
4. **"추천이 맞는지 어떻게 아나?"** — 가중치·θ 값과 축별 기여도(`breakdown`) 공개(화면 조정 UI는 없음, 로드맵) / 민감도 분석(±20%·θ 변동) / 검증 에이전트 / 오프라인 ML 교차 검증(게이트 통과 시만 부록 2 수록).
5. **"대출 한도를 어떻게 보장하나?"** — 보장하지 않음. 자격 부합 확인만, 상담 관문.
6. **"대출을 더 받으라고 유도하는 것 아닌가?"** — 상향 인사이트는 지속 후보 수·하향 마진·고지와 항상 동반.
7. **"결국 파라미터 룰 아닌가?"** — 탐색 계획은 대화 맥락 기반 LLM 판단 / 비용 정렬 닫힌 형태 + 조달·지속 제약 최적화.
8. **"임대료가 상권 단위 평균인데 정확한가?"** — 의도된 해상도 설계(역할 분담 서사) + 출처·해상도 화면 표기.
9. **"교통·생활 인프라는 어떻게 반영하나?"** — 대중교통 접근성은 w1의 3성분 중 하나로 반영합니다
   (최근접 역 승하차 × 거리 감쇠). 생활 인프라(집객시설)는 **수집만 완료했고 판정에는 반영하지
   않았습니다** — w1의 배후 성분은 상주인구 + 직장인구이며(`serving.py` `backing`), 집객시설
   반영은 로드맵입니다. 하지 않은 것을 했다고 적지 않기 위해 매핑 표에도 「판정 미반영」으로 표기합니다.

## B. 탐색 상세 10문항 (exploration spec §9 전사 — 답변 완성본은 해당 문서 참조)

10. N(B) 단조 가정은 언제 깨지나 → 지속 프론티어는 비단조 (서비스 철학의 수학적 구현)
11. 경계 수치의 그리드 오차 → 그리드 없음, 정렬값 자체가 경계 (오차 0)
12. 룰엔진 아닌가 → LLM 3역할 분리는 금융 AI의 설계
13. 대출 한도 유도 아닌가 → 단독 노출 불가 구조
14. 초기비용 추정 신뢰 → 공공 출처 4블록 + 구간 + 이중 표기
15. 조달 매칭이 한도를 보장하나 → 비보장 명시, 고지 동반
16. LLM 환각은 → 수치 접근 불가 구조 + 템플릿 폴백
17. 동시 사용자 확장성 → 세션당 DB 1회 + 인메모리 100ms, 병목은 LLM(필수 경로에서 제거)
18. 분기 데이터 한계 → 구조적 의사결정에 충분 + 기준일 표기
19. KB 내재화 시 → 행내 여신 데이터 결합 로드맵 (경쟁이 아니라 결합)

## C. 아키텍처 선택 1문항

20. **"근거 인용에 RAG(벡터 검색)를 왜 쓰지 않았나?"**
    → **검색할 질의가 없기 때문이다.** 인용 대상은 자격 필터가 이미 결정적으로 확정한 상품이고,
    상품→공고 원문 청크는 `doc_chunk_ref` 외래키로 직접 연결된다(한 문단이 여러 자금을 함께
    규정하는 공고가 있어 관계는 N:1이다). 입력이 자연어 질의가 아니라 상품 id이므로 유사도
    검색이 개입할 지점이 없다.
    더 중요한 것은 정확도다. 임베딩 유사도로 문단을 뽑으면 **다른 상품의 공고 문단이 특정 상품의
    자격 요건으로 붙는 오류**가 가능해진다. 금융상품 자격 요건 인용에서 이건 단순 오차가 아니라
    귀속 오류이며, id 직접 조회는 그 오류를 **구조적으로 만들 수 없다**. 스펙 §5-4의 「인용은
    검색이지 생성이 아니다」를 끝까지 밀면 도달하는 결론이 이것이다.
    부수적으로 pgvector 컨테이너·임베딩 배치·검색 P@k 골드셋이 전부 불필요해져, 심사위원이
    직접 실행하는 `docker compose up` 경로에 실패 지점을 추가하지 않는다.
    **재검토 시점**: 코퍼스가 수백 건 공고로 늘고 사용자가 문서에 자유 질의를 던지는 단계
    (확장 로드맵). 그때는 검색이 실제로 풀어야 할 문제가 생긴다.

## 예상 질문 — 「지역을 입력했는데 왜 다른 구가 추천되나」

**Q. 진단에서 「서울 마포구」를 입력했는데 상위 후보가 송파·관악입니다. 입력이 무시되나요?**

A. 무시되지 않습니다. 다만 **쓰이는 곳이 다릅니다.**

- 상권 후보 풀은 **서울 전역 1,059곳**(카페 기준)입니다. 이 서비스의 질문이 「어디가 좋은가」가
  아니라 **「내 한도로 어디까지 가능한가」**이기 때문입니다 — 예산으로 갈 수 있는 범위를
  자치구로 미리 좁히면, 사용자가 모르고 지나쳤을 선택지를 서비스가 먼저 지워 버립니다.
- 입력한 지역은 **지역 한정 금융상품의 자격 판정**에 쓰입니다(`regions = {서울}` 25건).
  「경기도 성남시」로 진단하면 자격 부합 상품이 11건 → 1건으로 줄어드는 것으로 확인할 수 있습니다.
- **화면 4는 진단에서 고른 자치구를 먼저 보여줍니다** (가정 #112·#113).
  예산을 조정한 뒤에도 같습니다. 「서울 전체로」 한 번이면 전역으로 돌아가고, 그 뒤로는
  자동 적용이 멈춥니다 — 사용자가 내린 결정을 화면이 계속 무르지 않습니다.
  자치구 드롭다운은 25개 구의 후보 수를 **전부** 보여 주므로, 좁혀진 상태에서도 다른 구가
  몇 곳인지가 화면에서 사라지지 않습니다.

  희망 지역에 지금 예산으로 갈 수 있는 곳이 **0곳이면 좁히지 않고** 서울 전체를 보여 주며,
  그 사실을 문장으로 적습니다. 빈 목록보다 정확하고, 예산을 올리면 다시 그 구로 좁혀집니다.
  (실측: 확정 예산 8,000만의 진입 가능은 노원구 6곳뿐이라 마포구는 0곳, 1억에서 20곳입니다.)

  ⚠️ **자치구 해상도는 상품 자격 판정에는 영향이 없습니다.** 적재된 26건의 지역 제약이
  25건 `{서울}` + 1건 무제약, 즉 전부 시/도 해상도이기 때문입니다(`EligibilityFilter`가 시/도를
  먼저 대조합니다). 실측: 마포구·강남구·노원구로 각각 진단하면 조달 시나리오·추천 목록·자격 부합
  상품이 **전부 동일**하고, 부산·미입력에서만 11건 → 1건으로 갈립니다. 즉 자치구가 하는 일은
  이제 **화면에서 좁혀 보는 것**이며, 그 사실을 화면의 필터 아래 캡션이 직접 적습니다.

## 예상 질문 — 「자격 매칭 P/R 1.000」의 사정거리

**Q. 자격 매칭 정확도 1.000이면 공고문 자격을 다 반영했다는 뜻인가요?**

A. 아닙니다. **「필터가 자격 축을 정확히 적용하는가」의 1.000**입니다.

- 골드는 적재본의 자격 축 컬럼을 사람이 읽고 적은 기대 라벨이라, 재는 것은 축 적용의 정확성입니다.
- **축이 공고문의 대상 요건을 다 담는가는 별도 문제**이며, 실제로 코드리뷰에서 「예비창업
  프로필에 기존 사업자 전용 상품이 노출된다」가 나왔습니다. 조치는 두 가지입니다 —
  ① 원문에 업력·가동 하한이 명시된 상품의 `existing_business_only` 를 채웠고(4 → 12건),
  ② 프로필로 확인할 수 없는 대상 한정 요건(장애인기업·사회적경제기업·인증기업·고용우수기업)을
  `target_group` 축으로 신설해 **확인되지 않으면 탈락**시킵니다(하향 안전).
- 남은 한계는 그대로 밝힙니다: 축 6종으로 신용평점·업종 세부·지역 사업 참여 이력까지 담지
  못합니다. 그래서 화면은 **상품 원문 인용을 함께 노출**하고, 문구도 「자격 요건 부합 상품
  확인(한도·승인은 기관 심사 사항)」으로 고정돼 있습니다.

## 예상 질문 — 「조달 시나리오 카드에는 왜 인용이 없나」

**Q. 근거 인용이 자랑거리라면서, 화면 2의 상품 카드에는 인용문이 안 보입니다.**

A. **그 두 상품에 인용할 원문이 없기 때문**이며, 없는 것을 채우지 않는 것이 설계입니다.

- 데모 프로필에서 카드에 편성되는 상품은 보수 = KB소상공인 보증서대출, 적극 = 소상공인
  정책자금대출입니다. 둘 다 출처 문서가 **브라우저로 인쇄된 웹 페이지**라 자격 요건 문단이
  원문에 존재하지 않습니다(인용 불가 문서 4건 중 2건). 그 자리에는 출처 기관·공고 URL·수집일이
  나갑니다.
- **카드 편성 규칙을 인용 보유 여부로 바꾸지 않았습니다.** 편성 규칙은 「필요분을 덮는 최소 한도」
  라는 결정적 규칙이고, 여기에 「인용이 있는 상품을 우선」을 섞으면 **화면에 잘 보이려고 자금
  계산을 바꾸는 것**이 됩니다. 표시 사정이 계산을 오염시키지 않는다는 원칙(스펙 §0-1)이 더 큽니다.
- 인용은 **역방향 판정 화면**에서 확인하실 수 있습니다 — 자격 부합 11건 중 **7건**에 공고 원문이
  그대로 붙어 있고, 화면 문장과 `finance_doc_chunk.text` 가 바이트 단위로 일치합니다.
