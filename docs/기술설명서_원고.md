## 1장. 주제 요구사항 ↔ 사용 데이터 매핑

> 3단계 서사 중 [0] 전제 · 심사위원이 대조하기 전에 우리가 먼저 대조한다.

| 주제문 요구 항목 | 사용 데이터 | 해상도 | 반영 위치 |
|---|---|---|---|
| 유동인구 | 서울시 길단위인구 + 상주·직장인구 | 표준단위구역 | w1 수요 |
| 상권 | 추정매출 · 경쟁밀도 · 상권변화지표 | 표준단위구역 | w2 · w3 · w4 |
| 교통 | 지하철역 좌표 + 역별 승하차 인원 | 역 단위 → 구역 조인 | w1 내 '대중교통 유입' 성분 |
| 생활 인프라 | 집객시설 | 표준단위구역 | w1 배후 보조 + 근거 패널 |
| 부동산 시세 | 부동산원 임대료 · 전환율 · 권리금 | 부동산원 상권 | 부담률 분자 · 초기비용 |
| 자금 계획·금융 수요 | 정책자금 · 보증 · 대출 구조화 DB (26건) | 상품 단위 | 조달 시나리오 · 갭 커버 |
| 대출·보증·정책금융 | 자격 필터 + exclusive_group + 원문 근거 | 상품 단위 | 시나리오 · 역방향 · 탐색 |

전 항목이 **서울 · 카페/음식점** 범위에서 실제로 수집·적재되어 있다. 상권 1,650곳,
업종별 점수 레코드 2,500행(카페 1,061 · 음식점 1,439), 정책자금 26건 · 원문 청크 22개.

## 2장. 아키텍처 — 숫자를 만드는 계층은 의도적으로 결정적이다

> 3단계 서사 중 [1] 사용자 이해 → [2] 결정공간 탐색 → [3] 결과 검증

```
[배치: Python]              [저장]                [서빙: Spring Boot]            [프론트]
공공 데이터 7종 ─→ 전처리 ─→ PostgreSQL ─┬→ 인터뷰어(폼 + 자유텍스트 파싱)      [1]
정책자금 문서 ─→ LLM 추출 ─→ 구조화 26건 ─┤  오케스트레이터
  + 사람 전건 검수            + 원문 청크 │  ├ 결정적 도구 계층 ──────── SSE ─→ React
                                        │  │   자격필터 / 비용계산 / 점수·부담률      +
                                        │  │   프론티어 / 역방향 판정            카카오맵
                                        │  ├ 결정공간 탐색 (이중 프론티어)      [2]
                                        │  └ 리스크 검증 에이전트 (1왕복)       [3]
```

LLM이 하는 일은 셋뿐이다 — **① 탐색 축 우선순위 계획, ② 구조화된 결과의 언어화,
③ 리스크 검증 반박문 생성.** 숫자를 만들거나 다시 계산하는 경로는 존재하지 않는다.
LLM에 전달되는 입력 JSON 밖의 수치는 출력에 나타날 수 없고, LLM이 장애일 때는 템플릿 문장이
그대로 최종본이 된다(데모 무중단 원칙).

> **【설계 원칙 ①】 룰엔진 아닌가?**
> 숫자를 만드는 계층은 **의도적으로** 결정적이다. 그 설계가 실제 데이터와 부합하는지는
> 오프라인에서 ML로 교차 검증했고(부록 2), 서빙에는 설명 불가능한 모델을 두지 않았다.
> 부록 2가 보여주는 것은 "모델이 잘 맞는다"가 아니라 **"데이터에 가장 잘 맞는 부호를 그대로
> 쓰면 안 되는 이유"** 다 — 경쟁밀도는 횡단면에서 부호가 뒤집힌다(내생성). 창업자에게
> 「점포가 많을수록 좋은 자리」라고 답하지 않기 위해, 우리는 설계를 데이터에 굴복시키지 않았다.

원문 근거 인용은 **유사도 검색을 쓰지 않는다.** 인용 대상은 자격 필터가 이미 확정한 상품이고,
상품→공고 청크는 외래키 직접 조회라 검색할 질의가 없다(한 문단이 여러 자금을 함께 규정하는
공고가 있어 관계는 N:1이다). 임베딩으로 뽑으면 다른 상품의 문단이
특정 상품의 자격 요건으로 붙는 오류가 가능해지는데, id 직접 조회는 그 오류를 구조적으로
만들 수 없다 — 「인용은 검색이지 생성이 아니다」를 끝까지 민 결과다 (예상 Q&A 20).

※ 위 다이어그램의 인용 경로 구현 여부는 CP4(D10) 판정 결과에 맞춰 확정한다.

## 3장. 데이터 — 해상도는 결함이 아니라 역할 분담이다

> 3단계 서사 중 [0] 전제

수집·적재한 데이터의 **기준일을 화면과 문서 모두에 상시 표기**한다. 추정이면 추정이라고 쓴다.

| 소스 | 기준일 | 화면 라벨 |
|---|---|---|
| 추정매출 | 2026-Q1 | 서울 상권분석 추정매출 (분기) — 당월매출 = 분기합 ÷ 3 |
| 임대료 | 2026-Q1 | 한국부동산원 ○○상권 분기 평균 (추정) |
| 권리금 | 2025년(전년 기준) | 한국부동산원 권리금 연간 조사 |
| 교통 | 2026-07 | 서울 지하철 승하차 (일평균, 환승역 합산) |
| 인테리어·시설 | 2025 | 공정위 가맹정보 2025 (가맹점 기준·상향) |

좌표는 전부 WGS84로 통일했고(원본 EPSG:5174/5179/5181 → pyproj 변환), 금액은 만원 단위 정수로
정규화했다. 대표면적은 인허가 데이터의 영업중 업소 소재지면적 중앙값을 썼다 —
**카페 29.2㎡ · 음식점 55.2㎡**(채움률 99.8%).

> **【설계 원칙 ③】 임대료가 상권 단위 평균인데 정확한가?**
> **변별은 구역 해상도, 임대 수준은 상권 해상도** — 이것은 타협이 아니라 역할 분담이다.
> 어느 구역이 더 좋은가는 표준단위구역 단위의 유동·매출·경쟁·변화 지표가 가른다.
> 얼마가 드는가는 부동산원 상권 단위 평균으로 추정하고, 그 사실을 라벨에 그대로 쓴다.
> 우리가 하지 않는 것은 **없는 해상도를 있는 것처럼 보이게 만드는 일**이다.

폴백도 숨기지 않는다. 구획도와 최신 분기 통계의 상권 코드가 어긋나는 구역은 자치구 평균으로
대체하고 그 사실을 플래그로 남긴다. 모든 가정은 `docs/assumptions.md`에 번호를 붙여 등재했다.

## 4장. 점수화 — 가중치를 공개하고, 흔들리는지도 공개한다

> 3단계 서사 중 [2] 결정공간 탐색

종합점수는 5개 축의 가중합이고, 각 축은 서울 전체 대비 **백분위**다(업종별로 따로 계산).

| 축 | 의미 | 기본 가중치 |
|---|---|---|
| w1 | 수요 — 유동 + (상주 + 직장) + 대중교통 유입 | 0.30 |
| w2 | 매출 수준 — 점포당 월 추정매출 | 0.20 |
| w3 | 경쟁 — 점포밀도의 역순 | 0.20 |
| w4 | 성장 — 상권변화지표 | 0.15 |
| w5 | 비용효율 — 점포당 매출 ÷ 환산임대료 | 0.15 |

대중교통 유입은 최근접 역의 일평균 승하차에 거리 감쇠 `exp(−d / 500m)`를 곱해 만든다.
가중치는 화면에서 **공개되고 조정 가능**하며, 부담률 상한 θ도 사용자가 움직일 수 있다.

> **【설계 원칙 ⑤】 추천을 신뢰할 수 있나?**
> 신뢰를 주장하는 대신 네 가지를 공개한다 — **가중치 공개 및 조정 가능**,
> **민감도 분석**(가중치 ±20% · θ 변동 12회 섭동에서 상위 3곳 유지율 카페 1.000 · 음식점 0.944),
> **리스크 검증 에이전트 통과**, **평가 하네스 성적표와 ML 교차 검증**(부록 1·2).
> 상위 후보가 특정 가중치 설정에 기대어 나온 결과가 아니라는 것을 같은 하네스로 재현할 수 있다.

## 8장. 평가·검증 — 재현 가능성 자체가 메시지다

> 3단계 서사 중 [3] 결과 검증

`cd ai && make eval` 한 번으로 부록 1·2의 AI 산출물 지표가 전부 재산출된다. 심사위원이 직접
실행할 수 있고, 실행하지 않아도 부록 수치로 충분하다 — **재현 가능성의 존재 자체**가 이 장의 요지다.

| 스위트 | 결과 |
|---|---|
| 정책자금 추출 정확도 | 상품 P 0.966 · R 1.000 · 필드 정확도 0.867 |
| 근거 충실도 | 적재 청크 verbatim 1.000 (22개) · coverage 26/26 |
| 민감도 | 카페 1.000 · 음식점 0.944 |
| 설계 교차 검증 | 게이트 **B** (R² 0.178 · ρ 0.514, 순위상관 경로) |
| 자격 매칭 P/R | P 1.000 · R 1.000 · F1 1.000 (프로필 14종 × 상품 26건 = 364쌍) |

클린 클론에 새 가상환경을 만들고 다른 파이썬 버전으로 다시 돌려도 게이트 판정과 전 대표 지표가
동일하게 나온다는 것을 실측했다. 상세와 해석은 부록 1·2.

## 9장. 사업성·기대효과 (1페이지)

> 재무 추정을 만들지 않는다. 이미 확보된 재료 두 개를 명문화한다.

**KB부동산과의 관계 — 결합의 프레이밍**

KB부동산은 **매물·시세의 관점**에서 공간을 본다. 본 서비스는 **자금·지속의 관점**에서 같은
공간을 본다. 창업자의 실제 의사결정은 두 관점이 만나는 지점 — 「이 매물을, 내 자금으로,
버틸 수 있는가」 — 에서 일어나며, 이 결합은 매물 플랫폼과 여신 역량을 함께 가진 KB만이
완성할 수 있는 동선이다.

**상담 관문으로서의 기대효과**

청년 창업자 약 35만 명, 창업 애로 1순위는 자금이다. 본 서비스는 자금 때문에 의사결정이 막히는
바로 그 지점에서 **자격 요건 부합 상품 확인 → 기관 상담**으로 연결되는 관문이다. 한도와 승인은
기관 심사 사항이며 본 서비스는 그것을 보장하지도, 보장한다고 말하지도 않는다.

공개 데이터만으로 만든 이 프로토타입은 내재화 시너지(행내 여신 데이터 기반 부담률 정밀화,
기존 여신 고객 이전·운영 컨설팅)의 **하한선**이다.

> 본 정보는 공개 자료 기반 정보 제공이며 대출 권유·중개·자문이 아닙니다.
