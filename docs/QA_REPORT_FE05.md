## 1. 반응성 — 클라이언트 재계산

실데이터 응답(`/api/recommend`, **1,061건 · 769 KB**)을 그대로 받아 화면이 슬라이더 1회당 수행하는
계산만 분리해 쟀다. Node 22 · Apple Silicon · 200회 평균(웜업 30회 제외).

| 구간 | 소요 |
|---|---|
| `JSON.parse` (769 KB) | 1.302 ms |
| `areas`: 범위 외 필터 + 점수 정렬 | 0.017 ms |
| `areas`: 판정 필터(적합) + 정렬 | 0.017 ms |
| `areas`: 정렬 변경(임대료 — 실제 재정렬) | 0.077 ms |
| `counts`: 판정 개수 집계 (FE-05 추가분) | 0.017 ms |
| `mapAreas`/`listAreas` slice | 0.016 ms |
| **합계 (파싱 + 정렬 + 집계)** | **1.34 ms** |
| 4x CPU 스로틀 환산 | 5.3 ms |
| 6x CPU 스로틀 환산 | 8.0 ms |

**클라이언트 재계산은 목표(<100ms)의 10분의 1 이하다.** 계약이 정렬·필터 쿼리를 두지 않고
전 필드를 실어 보내기로 한 결정(DECISIONS §10)이 반응성 면에서 옳았음을 뒷받침한다.

### 측정하지 않은 것 — 명시적으로 남긴다

- **카카오맵 마커 생성 비용**은 SDK가 브라우저를 요구해 헤드리스로 재지 못했다. 대신 코드
  경로를 검토해 아래 2절의 낭비를 제거했다. 실측은 브라우저 Performance 패널이 필요하다.
- **서버 왕복은 별도 문제다.** `/api/recommend`는 리스크 검증 LLM 왕복을 물고 있어 상위 후보의
  판정 구성이 바뀌면 **1.4~1.8초**가 걸린다(BE 실측, assumptions #64). 같은 구성 안에서는
  캐시로 ~10 ms다. 이 구간은 프론트가 줄일 수 없으므로 **직전 결과를 지우지 않고 흐리게 두는
  방식**으로 대응했다(`Recommend.columnsStale`) — 문구로 갈아 끼우면 지도가 매번 사라졌다
  다시 그려져 오히려 느리게 느껴진다.

## 2. 마커 재생성 — 선택 1회당 100개 → 2개

코드 검토에서 나온 결함이다. `KakaoMap`의 강조 효과가 `areas` 전체를 돌며 모든 마커에
`setImage`를 걸고 있었다. 마커 이미지는 매번 SVG data URI를 새로 만들므로, **목록에서 상권을
한 번 고를 때마다 마커 이미지 100개가 다시 생성**됐다(`MAP_MARKER_LIMIT = 100`).

고친 내용:

- 마커를 만들 때 선택 상태를 처음부터 반영한다(`selectedRef`로 읽어 의존성은 늘리지 않는다).
- 강조 효과는 **바뀐 둘만** 다시 칠한다 — 직전 선택 해제 + 새 선택 강조.

선택은 목록을 훑는 동안 가장 자주 일어나는 조작이라, 이 경로가 O(n)이면 후보가 늘수록
체감이 직접 나빠진다.

## 3. LLM 차단 상태 스윕

`OPENAI_API_KEY` 미설정 스택에서 전 동선을 돌렸다. BE-07 F2 항목과 같은 조건이다.

| LLM 개입 지점 | 응답 | 화면 표시 | 판정 |
|---|---|---|---|
| 진단 파싱 | `parse_source: "form_only"` | "폼 값만 사용" 배지 (`ParsedResult`) | ✅ |
| 탐색 계획(plan) | `plan` 1건 · 템플릿 `rationale` | 카드 헤더 계획 근거 1줄 상시 | ✅ |
| 언어화(refine) | **미송출** (`insight` 3 · `done` 1 · `refine` 0) | 템플릿 문장이 최종본, 별도 표시 없음 | ✅ |
| 리스크 검증 | `applied=false` · `skipped=true` | "리스크 검증 생략" 배지 + "기본 문안 (템플릿)" 출처 | ✅ |

`refine` 미도착 시 "문장을 다듬는 중…" 안내는 SSE 스트림 종료(`done`) 시점에 사라진다 —
무한 스피너가 남지 않는 것을 확인했다.

계약상 `refine`은 선택적 이벤트이므로 미송출이 규격 준수다(BE-07 3-1과 동일 판단).

## 4. BE로 넘긴 이슈

리스크 검증 결선(#96) 이후 FE 확인 과정에서 나온 것으로, **프론트에서 고칠 수 없다.**

### 4-1. 검증 에이전트가 범위 외 상권을 반박 대상으로 받는다

`RiskReviewAgent.recommendFacts`가 `areas` 상위 3곳을 사실로 넘기는데, 종합점수는 예산과
무관하므로 **어떤 예산에서든 같은 3곳**이 뽑힌다(방이동먹자골목·신림역 8번·황학코아루아파트).
확정 예산 6,000만원에서는 그 3곳이 전부 `OUT_OF_SCOPE`라, 화면이 걸러내어 **사용자가 볼 수
없는 상권**에 대한 반박이 만들어진다.

assumptions #64가 캐시 키 설계의 근거로 삼은 「예산이 움직이면 그 3곳의 판정만 바뀐다」는
성립하지만, 그 판정이 `범위 외`가 되는 구간을 고려하지 않았다. **범위 외를 제외한 상위 3곳**을
사실로 넘기면 해소된다.

FE는 검증 패널 `[1]단`을 **화면이 실제 제시한 결과**(범위 외 제외 + 판정 분포)로 서술하도록
고쳤으나, 서버가 넘기는 사실 자체는 그대로다.

### 4-2. 템플릿 반박문이 판정 분포와 무관한 고정 문장이다

`ReasonTemplate.recommendReview()`는 "…유의 판정 유지가 타당합니다"로 끝나는 고정 문장인데,
확정 예산 6,000만원에서는 판정 분포가 `범위 외 991 · 조건부 적합 70`으로 **유의 판정이 0곳**이다.
없는 판정을 유지하라는 반박이 된다.

이 문장은 LLM 장애 시 **최종본**이 되므로(스펙 §5-3) 심사 중 그대로 노출될 수 있다. 현재 키가
없는 스택에서는 모든 구간에서 이 문장이 나온다. `ReasonTemplate.reason()`이 이미 판정별로
문안을 나누고 있으므로 같은 방식이 적용 가능하다.

`objection_text`는 서버가 만든 문장이라 프론트가 상황에 맞게 고쳐 쓰면 §0-1과 충돌한다.
