## 2. 실행 추적 흐름

**태스크 이슈 27건 → PR 60건 → CI 4종 → 체크포인트 게이트.**
태스크 27건은 스크립트 1회 실행으로 라벨·마일스톤·일정 필드까지 붙은 이슈로 생성했고, 그
번호가 `#1`~`#27`이다. 이후 모든 PR은 본문에 `Closes #n` 을 달았고, PR이 develop에 병합되면
[develop-ci](../.github/workflows/develop-ci.yml) 가 통합 검증 → main 반영 → 참조 이슈 종료까지
자동으로 수행한다. 사람이 보드를 손으로 옮기는 단계는 "작업 시작 시 In Progress로 끌기" 하나뿐이다.

CI는 4종이다. 영역별 3종([frontend-ci](../.github/workflows/frontend-ci.yml) lint·용어 스윕·
vitest·build, [backend-ci](../.github/workflows/backend-ci.yml) gradle build,
[ai-ci](../.github/workflows/ai-ci.yml) ruff·pytest — 전부 Docker 빌드까지)과 통합 1종
(develop-ci: compose 전체 빌드 + 기동 스모크 + **실데이터 계약 게이트**)이다. 마지막 하나가
병합 게이트인 이유는 QA에서 확인한 사실 때문이다 — 단위·통합 테스트가 전부 픽스처 프로파일에서
돌아 그린이었는데도 실데이터 경로에 P0 결함이 살아 있었다([QA_REPORT_BE07.md](QA_REPORT_BE07.md)).

**왜 GitHub Projects인가** — 진행률의 원천 데이터가 PR 병합이기 때문이다. 보드가 GitHub 안에
있으면 `Closes #n` 병합이 곧 Done 이동이라 "보드 업데이트"라는 별도 노동이 사라진다.
Jira는 14일 일정에 세팅·관리 오버헤드가 과잉이었고, Notion은 PR 상태를 사람이 옮겨야 해서
마감 주간에 반드시 어긋난다고 봤다. 간트는 Projects v2의 Roadmap 뷰(Start/End 날짜 필드)로
대체했다.

## 3. 역할 분담

3인 팀이다. 커밋 제목의 태그는 **사람이 아니라 작업 영역**을 가리킨다 — 한 사람이 여러 영역을
오갔고, 태그는 그 커밋이 어느 영역을 건드렸는지를 나타낸다.

| 태그 | 영역 | 작업 커밋 | 비중 |
|---|---|---|---|
| `[AI]` | 배치 파이프라인 · 평가 하네스 | 76 | 33% |
| `[FE]` | 화면 1~3 · 지도 · SSE | 61 | 26% |
| `[CM]` | 공통 — 문서 · 계약 조율 · QA · 제출물 | 49 | 21% |
| `[BE]` | 서빙 · 결정적 도구 계층 · 에이전트 | 43 | 19% |

작업 커밋 232건 기준이며, 그중 태그가 없는 3건은 표에서 빠져 있다(비중 합계가 99%인 이유다).[^tags]
병합 커밋을 포함한 전체 402건 기준으로는
`[CM]` 115 · `[AI]` 84 · `[FE]` 62 · `[BE]` 53 이 되는데, `[CM]` 의 115건 중 62건은 develop-ci가
자동 생성한 `auto-merge develop into main` 커밋이라 사람의 작업량이 아니다. 그래서 위 표는
병합을 뺀 값을 쓴다.

## 5. 본선 개발 계획

기능 목록에 없는 항목이 "생각하지 못한 것"인지 "의도적으로 미룬 것"인지는 문서가 밝혀야 한다.
아래는 전부 후자이며, 순서는 스펙 §0-2가 예선 시작 시점에 고정해 둔 P1/P2 순서를 그대로 따른다
([최종_스펙문서.md](specs/최종_스펙문서.md) §0-2).

1. **P1 잔여 완결** — 근거문 캐시·개인화 언어화(§5-5) → 쇠퇴 상권 경고 뱃지 → 업종 추천.
   P1 ①(원문 근거 인용)·②(프론티어 미니 차트)는 예선에서 구현했으므로 ③~⑤가 남는다.
2. **동결 시점의 미해결 3건 정리** — ⓐ 추천 후보의 상한 없는 전량 렌더(지금은 상위 100곳
   상한으로 해소한 상태다) ⓑ 조달 시나리오 카드에 인용이 붙지 않는 건 ⓒ 검증 반박문이 확정
   예산 액수를 인용할 수 없는 건. ⓒ는 API 계약 변경을 수반하므로 계약 개정과 함께 다룬다.
3. **P2 — 대상의 확장** — 다회 왕복 자연어 인터뷰 · PDF 상담 리포트 · 실매물 연동 · 전국 확장
   (상권 코드 체계 검증이 지역마다 필요하다) · 버스 정류장·시간대별 승하차 반영.
4. **오프라인 검증 트랙** — 상관분석 교차검증 · 간이 백테스트 · 유사 상권 임베딩. 서빙 경로에
   모델을 두지 않는다는 원칙([PROJECT_RULES.md](PROJECT_RULES.md) §1)은 유지하며, 배치에서만 다룬다.

벡터DB(RAG)도 미룬 것에 속한다 — 인용 대상이 이미 확정된 상품이고 상품↔청크가 외래키로 N:1인
동안에는 검색할 질의가 없다. 코퍼스가 수백 건으로 늘고 사용자가 문서에 자유 질의를 던지는
단계에서 재검토한다.
